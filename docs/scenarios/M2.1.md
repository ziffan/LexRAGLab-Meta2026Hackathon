## Asumsi dan pilihan yang perlu disetujui operator

Spec diam atau ambigu di titik berikut. "Dipilih" = tafsir yang dipakai skenario; operator boleh mengganti, dan skenario yang terkait harus dihitung ulang.

1. **A1, arti `offset_found`, `text_matches`, `resolved_span`** (§9 hanya menyebut nama). Dipilih. Bila `start` dan `end` keduanya diberikan: `offset_found` = `0 ≤ start < end ≤ len(D)` (code point); `text_matches` = `offset_found` DAN `D[start:end] == teks_gold` (perbandingan persis, tanpa normalisasi, H-046); `resolved_span` = `{start, end}` bila `offset_found`, selain itu `null`. Bila keduanya `null`: cari `teks_gold` di `D`; tepat satu kemunculan → `resolved_span` kemunculan itu, kedua bendera `true`; selain itu kedua bendera `false`, `resolved_span = null`. `teks_gold` kosong → kedua `false`.
2. **A2, `teks_gold` muncul ≥ 2 kali dan tanpa offset.** Dipilih: tidak terselesaikan (`false/false/null`), operator harus Edit. Alternatif: kemunculan pertama dipakai diam-diam (berisiko gold salah tempat; S10 baris L2).
3. **A3, offset sebagian** (`start` terisi, `end` `null`, atau sebaliknya). Dipilih: offset diabaikan, diperlakukan seperti tanpa offset (cari teks). Alternatif: tidak valid (`false/false/null`).
4. **A4, offset diberikan tetapi salah.** Dipilih: tanpa pencarian cadangan; `text_matches = false` walau teks ada di tempat lain (§5: "offset Spark harus cocok"). Alternatif: cadangan ke kemunculan tunggal.
5. **A5, usulan yang gagal semantik.** Dipilih: usulan dengan `doc_id` ≠ dokumen yang diminta atau `mode` ∉ `modes` yang diminta dibuang (tidak jadi `ProposalRecord`; isi log run tidak diasersi di skenario ini); usulan dengan span gagal (A1) **disimpan** dengan `validation` salah, karena U6 dan W5 mengharuskan operator melihatnya dan bisa Edit/Reject. Alternatif: semua kegagalan dibuang (bentrok dengan U6 "hanya Edit atau Reject").
6. **A6, batas jumlah usulan per panggilan** (`config`, §5). Dipilih: per run (per mode), diterapkan **setelah** pembuangan A5, urutan keluaran dipertahankan, kelebihan dibuang. Alternatif: batas atas atas keluaran mentah (S13 membedakan).
7. **A7, kode galat W5/W4.** Dipilih: nilai `decision` di luar enum (termasuk `usulan`, huruf besar, `null`, hilang) → `400 invalid_request`; `proposal_id` tak dikenal → `404 not_found`; kunci tak dikenal di badan atau di `edited`, `edited` bukan `null` untuk `disetujui`/`ditolak`, `edited` `null` untuk `diubah`, isi `edited` tidak sah, `disetujui` pada usulan `text_matches = false` → `422 validation_failed`; transisi dari status ≠ `usulan` → `409 invalid_transition`. API §5 hanya menetapkan yang terakhir; sisanya pilihan penyusun. Alternatif untuk `disetujui` pada span gagal: `409 invalid_transition`.
8. **A8, `disetujui` dengan `edited` terisi (KEPUTUSAN OPERATOR WAJIB; S8, S9(c), S30 mengunci pilihan).** API §5 berbunyi "tidak boleh disetujui tanpa `edited`", yang secara literal bisa berarti `disetujui` + `edited` sah. Tiga pilihan:
   - **I (dipilih):** `edited` hanya sah bersama `diubah`; `disetujui` + `edited` -> `422 validation_failed`. Konsekuensi: usulan dengan span gagal hanya bisa lewat `diubah` (cocok dengan U6: Approve nonaktif); `review_status` mencerminkan jujur ada-tidaknya edit (H-035); S8 (1) dan S9(c) berlaku seperti ditulis.
   - **II:** `disetujui` + `edited` valid diterima dan `Item` memakai `edited`. Konsekuensi: dua jalur untuk perbuatan yang sama; `review_status = disetujui` bisa menyembunyikan isi yang berbeda dari `body` (melemahkan pembeda `diubah`, H-035), kecuali sistem diam-diam menulis `diubah` (label keputusan operator tidak sama dengan yang tersimpan). S9(c) menjadi 200 (Item dari `edited`), S8 (1) tetap bila `edited` tidak dikirim; perlu skenario tambahan untuk `review_status` yang dicatat.
   - **III:** `edited` diabaikan pada `disetujui`. Konsekuensi: edit operator hilang diam-diam; paling berisiko, tidak direkomendasikan.
9. **A9, isi `edited`.** Dipilih: `query` tidak kosong setelah dipangkas; `mode` ∈ {`literal`, `parafrase`} (boleh beda dari mode usulan); `gold_spans` tidak kosong, tiap elemen integer JSON (bukan 10.0, bukan string) dengan `0 ≤ start < end ≤ len(D)` code point. Butir Spark tanpa gold ditolak (butir wajib-tolak adalah kontrol operator, H-011). Tumpang-tindih antar-span tidak diatur dan tidak diuji. Alternatif: `gold_spans: []` diterima.
10. **A10, parafrase.** Mode parafrase mensyaratkan pertanyaan tanpa kata kunci literal dari span (§5), tetapi validasi semantik §5 hanya menyebut span. Dipilih: sistem **tidak** memeriksa tumpang-tindih leksikal (operator yang menilai); mode tersimpan apa adanya (S10 PA6). Alternatif: sistem memberi peringatan pada kartu.
11. **A11, kestabilan `proposal_id`.** Dipilih: id diturunkan deterministik dari kunci cache run dan indeks usulan, sehingga W4 ulang (cache hit) mengembalikan id yang sama dan tidak membuat duplikat (S12). Format id bebas.
12. **A12, kunci korpus (PERUBAHAN KONTRAK `docs/DATA-CONTRACTS.md` §9 bila dipilih I; butuh keputusan operator: dicatat di log keputusan operator dulu, lalu kontrak, baru kode; S18 terkunci pada pilihan ini).** `ProposalRecord` §9 tidak punya `clean_sha256`, padahal `Item` §4 mewajibkannya. Tiga pilihan:
   - **I (dipilih):** tambah field `ProposalRecord.clean_sha256` (diisi saat usulan dibuat); W5 `disetujui`/`diubah` dengan hash dokumen sekarang berbeda -> `409 hash_mismatch`; `ditolak` tetap boleh. Konsekuensi: kontrak §9 berubah (struktural, AGENTS.md "Saat keputusan berubah"); berkas usulan lama tanpa field perlu aturan migrasi; S18 berlaku.
   - **II:** tanpa pemeriksaan; `Item.clean_sha256` = hash dokumen saat keputusan. Konsekuensi: kontrak tak berubah, tetapi bila korpus dibekukan ulang antara usulan dan keputusan, offset gold bergeser diam-diam (H-046 menuntut gold dihitung ulang); S18 dihapus.
   - **III:** hash diambil dari `RunRecord.clean_sha256` (sudah ada di §12) lewat `ProposalRecord.run_id`; W5 membandingkannya dengan hash dokumen sekarang. Konsekuensi: §9 tak berubah, hasil S18 sama; W5 bergantung pada penyimpanan run (run hilang = usulan tak bisa diputuskan). Penyusun menilai III paling murah, tetapi ini pilihan operator.
13. **A13, tata simpan.** Dipilih: `Item` baru dari W5 ditulis ke berkas versi baru di `data/butir/` (tidak ke `uupt.v1.jsonl`, milik operator, README: "Versi tidak ditimpa"); `ProposalRecord` disimpan terpisah dari `Item`. Test hanya menegaskan perilaku (byte v1 tetap, muat ulang menghasilkan gabungan, LF murni), bukan nama berkas.
14. **A14, `SplitRecord`.** W5 tidak menulis `SplitRecord`; penugasan stratum untuk butir baru dan kenaikan `split_version` (EVAL-SPEC §8 butir 5) terjadi di pekerjaan split/grid (M1.4). Alternatif: W5 memicu penugasan. Tidak diuji di sini (lihat "Belum tercakup").
15. **A15, atomisitas dan kode galat 5xx.** Kontrak API tidak punya kode untuk kegagalan penyimpanan. Dipilih: respons non-2xx berbentuk `{"error": {"code", "message"}}` (nama kode bebas; disarankan menambah `500 storage_error`), status usulan dan jumlah butir tak berubah (U6 "Nothing was changed").
16. **A16, `modes` W4.** Dipilih: daftar kosong atau nilai di luar enum → `400 invalid_request` tanpa panggilan Spark; duplikat (`["literal","literal"]`) dilebur jadi satu panggilan. Alternatif duplikat: `400`.
17. **A17, keluaran Spark rusak** (tidak sesuai skema `ProposalD`): `502 model_error`, tidak ada `ProposalRecord`, tidak di-cache sebagai sah (SPARK-ROLES §1). Alternatif kode: `422 schema_invalid`.
18. **A18, laporan per asal.** Dipilih: fungsi murni atas `Item` + `ItemMetrics` + `SplitRecord`, parameter `split` (laporan default `held_out`, EVAL-SPEC §9); rata-rata **per butir** (bukan gabungan karakter), butir ber-`null` dikeluarkan dari rata-rata; `item_id` di `ItemMetrics` yang bukan `Item` sah (mis. id usulan) → galat keras. Alternatif galat tersebut: baris diabaikan diam-diam. Pemecahan per mode di dalam asal dan penghitungan metrik bukan bagian M2.1.
19. **A19, konteks kartu U6.** Dipilih: jumlah baris sebelum/sesudah `k` dari konfigurasi (test memakai `k = 1`); baris = pemisahan di LF, LF penutup tidak membentuk baris tambahan; offset sorot relatif terhadap awal konteks, code point.
20. **A20, seleksi teks di form Edit.** Browser memberi indeks UTF-16; kontrak memakai code point. Dipilih: konversi di frontend; batas di tengah pasangan surrogate digeser keluar ke batas code point. Alternatif: seleksi seperti itu ditolak.
21. **A21, replay.** Perilaku W5 di mode replay tidak ditentukan spec; W4 di replay tanpa run tersimpan → `409 replay_no_stored_run` (API §1). W5-replay tidak diuji.
22. **A22, duplikasi lintas run.** Dua run berbeda (mis. `prompt_hash` berbeda) yang mengusulkan span sama tidak di-dedup. Tidak diuji.
23. **A23, jumlah `RunRecord` pada respons W4.** API §3 menulis `ProposalRecord[]` + `RunRecord` (tunggal). Dipilih: satu `RunRecord` per mode yang dipanggil (konsisten dengan kunci cache per mode); `docs/API.md` W4 diperbarui bila diterima. Alternatif: satu `RunRecord` agregat (biaya/`usage` tergabung).
24. **A24, kunci badan W5 yang dihilangkan.** Dipilih: `operator_note` dihilangkan = `null`; `edited` dihilangkan = `null`. Alternatif: kunci wajib hadir (hilang -> 422). Diuji di S9(h).
25. **A25, `query` disimpan apa adanya** (tidak dipangkas); hanya divalidasi "tidak kosong setelah dipangkas". Alternatif: disimpan terpangkas. Diuji di S7 (e15).
26. **A26, urutan prioritas galat W5.** Dipilih: (1) `404` id tak dikenal; (2) `400`/`422` bentuk badan dan nilai `decision`; (3) `409 invalid_transition`; (4) `409 hash_mismatch` (bila A12 I/III); (5) `422` isi `edited` dan gerbang span. Alternatif: bentuk badan sebelum `404`, atau `409` sesudah `422`. Diuji di S30.
27. **A27, seam uji di kode produksi.** S15 (balapan deterministik) dan S16 (kegagalan penyimpanan) membutuhkan penyimpan yang dapat disuntik (hook sebelum-tulis, penyuntik galat). Skenario tidak menetapkan antarmukanya; eksekutor memilih dan operator menyetujui di review kode. Alternatif: hanya uji probabilistik (20 putaran), yang bisa meloloskan balapan.

## Skenario

### S1 — Tiga transisi sah dari `usulan`
- Masukan: W4 `{doc_id: doc-x, modes: [literal]}` menghasilkan L1 (valid, `review_status = usulan`). Tiga salinan segar, tiap salinan satu W5: (a) `{decision: disetujui, edited: null, operator_note: "n1"}`; (b) `{decision: diubah, edited: {query: "QE", gold_spans: [{start:27,end:43}], mode: "literal"}, operator_note: null}`; (c) `{decision: ditolak, edited: null, operator_note: "n3"}`.
- Langkah hitung: tiap transisi memeriksa status awal = `usulan` lalu menulis status tujuan dan `reviewed_at` = jam suntikan.
- Jawaban yang diharapkan: (a) 200, `review_status = disetujui`, `reviewed_at = 2026-10-29T10:00:00Z`, `item_id` terisi, ada tepat 1 `Item`. (b) 200, `diubah`, `item_id` terisi, 1 `Item`. (c) 200, `ditolak`, `item_id = null`, 0 `Item`, `operator_note = "n3"`, `reviewed_at = 2026-10-29T10:00:00Z`.
- Bug yang ditangkap: salah satu dari tiga transisi tidak diimplementasikan; `ditolak` tetap membuat butir; `reviewed_at` tidak diisi atau bukan UTC (`Z`); `item_id` tidak ditautkan.

### S2 — Semua transisi dari status akhir ditolak (9 kasus)
- Masukan: tiga usulan dibawa lewat jalur sah ke status akhir dengan catatan `n0`: P-a `disetujui` (dari L1), P-b `diubah` (dari PA1, `edited` valid), P-c `ditolak` (dari PA6). Simpan salinan byte `ProposalRecord`, daftar `Item`, dan isi berkas butir. Lalu untuk tiap P ∈ {P-a, P-b, P-c} kirim W5 dengan `decision` ∈ {disetujui, diubah (edited valid), ditolak}, `operator_note = "n1"`: 3 × 3 = 9 permintaan.
- Langkah hitung: status awal ≠ `usulan` pada semua 9.
- Jawaban yang diharapkan: semua 9 `409 invalid_transition` (termasuk status yang sama, mis. `disetujui` → `disetujui`). Setelah tiap permintaan, `ProposalRecord` identik byte-per-byte (`review_status`, `edited`, `operator_note = "n0"`, `reviewed_at`, `item_id`), jumlah `Item` tetap 2 (P-a, P-b), isi berkas butir identik.
- Bug yang ditangkap: pintu belakang `ditolak → disetujui`; `disetujui` dua kali membuat butir ganda; `diubah` menimpa `edited` atau `body` yang sudah tersimpan; `operator_note`/`reviewed_at` ditimpa walau transisi gagal; transisi dicek hanya "bukan sama dengan tujuan" dan bukan "harus `usulan`".

### S3 — Nilai `decision` dan id tidak sah
- Masukan: pada usulan L1 berstatus `usulan`: W5 dengan `decision` = `"usulan"`, `"approved"`, `"DISETUJUI"`, `"Disetujui"`, `null`, atau kunci `decision` hilang. Lalu `proposal_id = "tidak-ada"` dengan `decision = ditolak`.
- Langkah hitung: enum sah hanya `disetujui`, `diubah`, `ditolak` (huruf kecil persis).
- Jawaban yang diharapkan: enam permintaan pertama `400 invalid_request` (A7); id tak dikenal `404 not_found`. `ProposalRecord` L1 tidak berubah, 0 `Item`.
- Bug yang ditangkap: `decision = usulan` diterima sebagai no-op atau mengembalikan usulan ke antrean; pencocokan tak peka huruf menerima `DISETUJUI`; `null` dianggap `ditolak`/`disetujui` (nilai bawaan); id tak dikenal menghasilkan 500 atau membuat rekaman baru.

### S4 — Tidak ada jalur dari `usulan` ke evaluasi (H-006)
- Masukan: direktori data sementara dengan berkas butir operator berisi 2 butir (`OP1`, `OP2`, `origin = operator`). W4 `{doc-x, [literal, parafrase]}` menghasilkan 13 usulan (S11). Tidak ada keputusan. Lalu: (i) muat himpunan butir untuk evaluasi, `items_summary`, dan butir di snapshot; (ii) tolak L1 dan muat lagi; (iii) setujui PA1 dan muat lagi; (iv) muat ulang dari disk di proses baru.
- Langkah hitung: himpunan butir = butir operator + `Item` yang lahir dari W5 (`disetujui`/`diubah`).
- Jawaban yang diharapkan: (i) {OP1, OP2}, `n_items = 2`; (ii) tetap {OP1, OP2}; (iii) 3 butir: OP1, OP2, butir PA1 dengan `origin = spark_disetujui`; (iv) sama dengan (iii); (v) setelah (iii), berkas catatan usulan dibuang seluruhnya dan butir dimuat ulang: tetap 3 butir (himpunan butir tidak ditentukan dari catatan usulan).
- Bug yang ditangkap: usulan `usulan` ikut dimuat sebagai butir (sumber butir = tabel usulan); `ditolak` ikut dimuat; butir hilang setelah proses dimulai ulang (hanya di memori); `items_summary` menghitung usulan.

### S5 — `Item` yang lahir dari `disetujui`
- Masukan: DX, L1 (`QL1`, literal, resolved `[27,43)`), W5 `{decision: disetujui, edited: null, operator_note: "n1"}`, jam `2026-10-29T10:00:00Z`.
- Langkah hitung: field `Item` §4 dari `ProposalRecord`: query = `body.query`; gold = `[resolved_span]`; mode = `body.mode`; sisanya konstanta jalur.
- Jawaban yang diharapkan: `Item` = {`family: uupt`, `query: "QL1"`, `doc_id: doc-x`, `gold_spans: [{start:27,end:43}]`, `clean_sha256: hx1`, `mode: literal`, `origin: spark_disetujui`, `review_status: disetujui`, `proposal_id: <id L1>`, `reference_date: null`, `scene_checked: false`, `operator_note: "n1"`, `created_at: 2026-10-29T10:00:00Z`}, `id` string tak kosong dan unik. `ProposalRecord.item_id` = `Item.id`; `review_status = disetujui`; `body` tak berubah; respons W5 memuat keduanya.
