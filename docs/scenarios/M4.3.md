## Definisi bersama

**Tokenizer mainan `toy-ws` versi `1`.** Token = deretan maksimal karakter bukan-spasi; offset `[start,end)` code point. Test nyata memakai tokenizer fake/injeksi dengan perilaku ini, bukan tokenizer H-014.

**Dokumen UU PT mainan** (`family = uupt`, teks bersih = teks mentah, tanpa anotasi):
- `d1` = `a0 a1 a2 a3 a4 a5 a6 a7 a8 a9` (10 token, panjang 29). Token ke-i (mulai 0) menempati `[3i, 3i+2)`. Potongan token i..j = `[3i, 3j+2)`.
- `d2` = `b0 b1 b2 b3 b4 b5` (6 token, panjang 17), aturan offset sama.
- `d1x` = `d1` dengan token `a9` diganti `x9` (panjang tetap 29, SHA-256 mentah lain). `d1n` = `d1` plus satu `\n` di akhir (panjang 30). `d3` = dokumen UU PT ketiga sembarang.
- SHA-256 mentah `H(d)` dan `clean_sha256` dihitung test dengan `hashlib` atas byte UTF-8; skenario hanya menyatakan sama/beda.

**Dokumen akta mainan** (`family = akta`), `da`, panjang 45, `⏎` = `\n`:
`Pasal 1⏎Aa bb.⏎Pasal 2⏎Cc dd.⏎Pasal 3⏎Ee ff.⏎` — `Pasal 1⏎` = `[0,8)`, `Aa bb.⏎` = `[8,15)`, `Pasal 2⏎` = `[15,23)`, `Cc dd.⏎` = `[23,30)`, `Pasal 3⏎` = `[30,38)`, `Ee ff.⏎` = `[38,45)`.

**Chunker injeksi (fake).** Test M4.3 menguji logika profil, bukan chunker (M1.1). Test memakai chunker fake yang mengembalikan potongan menurut tabel berikut (kunci = chunker + parameter + versi tokenizer + isi skema); kunci yang tidak ada di tabel melempar galat keras (bukan daftar kosong):

**Setting baku** (`family = uupt` kecuali disebut):

## Skenario

### S1 — Round-trip UU PT: potongan identik
- Masukan: ekspor profil `P1` (W7) untuk korpus {d1, d2}; salin respons; impor (W8) pada korpus yang sama.
- Langkah hitung: bangun ulang dari `profile.setting` → d1 `[0,11) [9,20) [18,29)`, d2 `[0,11) [9,17)` = 5 potongan, urutan seperti definisi `P1`. `chunk_id` tiap potongan sama dengan yang dibangun saat ekspor (sama `doc_id`, offset, `chunker_key`). `chunk_set_hash` bangun ulang = `profile.chunk_set_hash` = hash dari 5 `chunk_id` tadi.
- Jawaban yang diharapkan: HTTP 200 `{"ok": true, "chunk_set_hash_matches": true}`; daftar `(doc_id,start,end)` hasil bangun ulang sama persis (5 elemen); `profile.corpus_hash` = `corpus_hash` yang dihitung dari {d1,d2}. Variasi: bangun ulang di dua proses terpisah dengan `PYTHONHASHSEED=1` dan `=2` memberi `chunk_set_hash` yang sama.
- Bug yang ditangkap: hash memuat `created_at` atau `run_id`; hash bergantung urutan dict/set atau seed hash Python; bangun ulang memakai parameter default config alih-alih `profile.setting`; offset dihitung dalam token alih-alih code point.

### S2 — Profil mandiri terhadap perubahan config
- Masukan: ekspor `P1`. Ubah config suntikan: `config/grid.fixed_size` jadi 512/64, sehingga `config_hash` aktif ≠ `profile.config_hash`. Impor.
- Langkah hitung: bangun ulang memakai `setting` 4/1 dari profil → 5 potongan yang sama dengan S1.
- Jawaban yang diharapkan: 200 `{ok:true, chunk_set_hash_matches:true}`; tidak ada 409.
- Bug yang ditangkap: bangun ulang dari config aktif (hash beda); menolak impor karena `config_hash` beda.

### S3 — Hash potongan peka terhadap isi potongan; pemalsuan terdeteksi
- Masukan: (a) profil `P1` dan `P2` pada korpus yang sama. (b) profil `P1` yang `setting.overlap_tokens` diubah 1 → 2 (dan `setting_id` dihitung ulang agar lolos validasi) dengan `chunk_set_hash` tetap milik `P1`. (c) profil `P1` yang `chunk_set_hash`-nya diubah satu karakter heks.
- Langkah hitung: (a) `P1` 5 potongan, `P2` 6 potongan: `setting_id` dan `chunk_set_hash` berbeda. (b) bangun ulang dengan overlap 2 → 6 potongan → hash `P2` ≠ klaim `P1`. (c) bangun ulang 5 potongan benar → hash ≠ klaim rusak.
- Jawaban yang diharapkan: (a) dua `chunk_set_hash` berbeda. (b) dan (c): HTTP 200 `{"ok": false, "chunk_set_hash_matches": false}` (A5); bukan 409, bukan 500, bukan `ok:true`.
- Bug yang ditangkap: impor menyalin hash klaim ke hasil dan melaporkan cocok; hash dihitung dari `setting` saja, bukan dari potongan; hanya membandingkan jumlah potongan; 500 saat tak cocok.

### S4 — Korpus beda ditolak dengan pesan jelas
- Masukan: profil `P1` (dari {d1,d2}); korpus aktif, satu uji per varian: (a) {d1x, d2}; (b) {d1n, d2}; (c) {d1} (d2 hilang); (d) {d1, d2, d3}; (e) seperti (a) **dan** `profile.chunk_set_hash` dirusak.
- Langkah hitung: `corpus_hash` aktif (a)–(e) ≠ `profile.corpus_hash` (pasangan `(doc_id, sha256)` atau himpunan dokumen berbeda).
- Jawaban yang diharapkan: semua varian HTTP 409, `error.code = "hash_mismatch"`, `error.message` memuat kalimat persis `Profile corpus hash does not match loaded corpus` dan 12 heks pertama `corpus_hash` profil serta `corpus_hash` aktif; tanpa stack trace. Chunker fake 0 panggilan; `profiles/` dan `runs/` tak berubah. Varian (e) tetap 409, bukan `ok:false`.
- Bug yang ditangkap: menolak hanya bila jumlah dokumen beda ((a),(b) lolos); hash dari `char_count`; membangun ulang lalu 200 `ok:false` alih-alih menolak; urutan cek terbalik (e); pesan generik tanpa hash; pesan berisi stack trace.

### S5 — Komposisi `corpus_hash`
- Masukan: (a) korpus dimuat urutan `[d2, d1]` vs `[d1, d2]`. (b) korpus {`d1` berisi teks d2, `d2` berisi teks d1} (isi bertukar `doc_id`; himpunan SHA mentah sama). (c) korpus akta berubah (`da` → `da'`) sementara korpus UU PT tetap {d1,d2}.
- Langkah hitung: A1: (a) pasangan `(doc_id,sha)` terurut menurut `doc_id` sama → hash sama. (b) pasangan `(d1,H(d2)), (d2,H(d1))` ≠ `(d1,H(d1)), (d2,H(d2))` → hash beda. (c) hanya dokumen keluarga `uupt` ikut → hash sama.
- Jawaban yang diharapkan: (a) `corpus_hash` sama, impor `P1` 200 `ok:true`. (b) `corpus_hash` beda → 409 `hash_mismatch` (bila operator memilih alt. A1(a): hash sama, tetapi impor 200 `{ok:false, chunk_set_hash_matches:false}`; apa pun pilihannya, tidak boleh `ok:true`). (c) `corpus_hash` UU PT sama; impor `P1` 200 `ok:true`.
- Bug yang ditangkap: hash bergantung urutan muat; hash himpunan SHA tanpa `doc_id` yang meloloskan penukaran; hash global lintas keluarga ((c): profil UU PT batal karena berkas akta berubah).

### S6 — `loader_rules_version` atau `clean_sha256` beda dengan SHA mentah sama
- Masukan: profil `P1` dengan `loader_rules_version = "1"`. Korpus aktif {d1,d2} dengan SHA mentah sama, tetapi pemuat suntikan memakai `loader_rules_version = "2"` dan menghasilkan `clean_sha256` beda untuk `d1`. Varian: versi aturan sama, hanya `clean_sha256` beda.
- Langkah hitung: `corpus_hash` (SHA mentah) sama; `loader_rules_version` beda; gabungan `clean_sha256` (A6) beda.
- Jawaban yang diharapkan: 409 `hash_mismatch`; pesan menyebut `loader rules` / `clean text`, tidak hanya kalimat korpus. Chunker fake 0 panggilan. Varian juga 409.
- Bug yang ditangkap: hanya memeriksa SHA mentah sehingga offset di atas teks bersih lain dipakai diam-diam (offset tak valid, H-046).

### S7 — Skema tertanam dipakai, bukan skema aktif (akta)
- Masukan: korpus {da}. Penyimpanan skema akta punya v1 dan v2 (v2 = koreksi operator, `parent_version = 1`); versi aktif = v2. Ekspor `PA1` (`schema_version = 1`). Impor.
- Langkah hitung: ekspor menyertakan **tubuh v1 utuh** (A12) di `profile.schema`. Bangun ulang dari skema tertanam: `[0,15) [15,30) [30,45)` (3 potongan). Dari v2 aktif: `[8,15) [23,30) [38,45)` → hash beda.
- Jawaban yang diharapkan: `profile.schema` sama (kanonik) dengan `SchemaRecord.body` v1; `profile.setting.schema_version = 1`; impor 200 `{ok:true, chunk_set_hash_matches:true}` dengan potongan `[0,15) [15,30) [30,45)`. Varian: v1 dihapus dari penyimpanan sebelum impor: tetap `ok:true`.
- Bug yang ditangkap: ekspor mengisi skema aktif terbaru; hanya menyimpan nomor versi sehingga impor bergantung penyimpanan; bangun ulang dari skema aktif; skema diringkas.

### S8 — Blok `held_out` UU PT: hanya held-out, pada setting itu, rata-rata per butir
- Masukan: setting `P1`. `ItemMetrics` suntikan (angka sudah dihitung M1.2; M4.3 hanya mengagregasi):

| Butir | split | origin | mode | gold_chars | covered | span_recall | retrieved_tokens | gold_tokens | token_precision | fully_covered |
|---|---|---|---|---|---|---|---|---|---|---|
| h1 | held_out | operator | literal | 10 | 10 | 1,0 | 8 | 4 | 0,5 | true |
| h2 | held_out | operator | parafrase | 20 | 15 | 0,75 | 10 | 2 | 0,2 | false |
| h3 | held_out | spark_disetujui | parafrase | 5 | 0 | 0,0 | 6 | 0 | 0,0 | false |
| h4 | held_out | operator | literal | 0 | 0 | null | 7 | 0 | null | null |
| t1 | tune | spark_disetujui | literal | 10 | 10 | 1,0 | 10 | 9 | 0,9 | true |
| t2 | tune | operator | parafrase | 10 | 10 | 1,0 | 10 | 8 | 0,8 | true |

  Distraktor: `ItemMetrics` untuk `P2` pada h1–h4 semuanya `span_recall = 1,0`, `token_precision = 1,0`.
- Langkah hitung: held-out `P1` = h1–h4 (4 butir; 3 operator, 1 spark_disetujui). Butir bergold = h1, h2, h3. `mean_span_recall = (1 + 0,75 + 0)/3 = 7/12 ≈ 0,583333`. `mean_token_precision` atas non-null = (0,5 + 0,2 + 0)/3 = 7/30 ≈ 0,233333. `fully_covered`: h1 saja dari {h1,h2,h3} → `{covered:1, total:3}`.
- Jawaban yang diharapkan: `held_out = {n_items: 4, by_origin: {"operator": 3, "spark_disetujui": 1}, mean_span_recall: 7/12, mean_token_precision: 7/30, fully_covered: {covered: 1, total: 3}}` (float toleransi 1e-9).
- Bug yang ditangkap: rata-rata atas semua butir tune+held-out (recall `(1+0,75+0+1+1)/5 = 0,75`); atas tune saja (1,0); butir tanpa gold dihitung 0 (recall `1,75/4 = 0,4375`, precision `0,7/4 = 0,175`); rasio gabungan (recall `25/35 ≈ 0,714`, precision `6/24 = 0,25`); `fully_covered.total = 4`; kebocoran metrik setting lain (`P2` = 1,0); `n_items = 3`; `by_origin` menghitung tune.

### S9 — Held-out tanpa butir bergold; tanpa hasil grid
- Masukan: (a) `P1` dengan held-out hanya {h4} (tanpa gold) plus butir tune sembarang. (b) `P1` UU PT tanpa hasil grid sama sekali.
- Langkah hitung: (a) butir bergold di held-out = 0 → rata-rata tak terdefinisi (A10). (b) tidak ada angka held-out.
- Jawaban yang diharapkan: (a) 200; `held_out = {n_items: 1, by_origin: {"operator": 1, "spark_disetujui": 0}, mean_span_recall: null, mean_token_precision: null, fully_covered: {covered: 0, total: 0}}`; tidak ada `NaN`, tidak ada pembagian nol, JSON valid. (b) 422 `validation_failed` (A11), tidak ada profil dengan `held_out` berisi nol palsu.
- Bug yang ditangkap: `ZeroDivisionError`/`NaN` (JSON tidak valid); `0.0` palsu yang terbaca "recall nol"; `held_out = null` untuk UU PT; profil diekspor tanpa dasar.

### S10 — Profil akta: tanpa held-out, tanpa split
- Masukan: ekspor `PA1` (korpus {da}); lima butir akta a1–a5 dengan `ItemMetrics` (S12); `SplitRecord` akta tidak ada.
- Langkah hitung: H-054: akta tanpa split → `held_out = null`; `ItemMetrics.split = null` (H-059).
- Jawaban yang diharapkan: `profile.held_out` adalah `null` persis (bukan objek berisi nol, bukan `{}`); `profile.family = "akta"`; `profile.schema` berisi skema akta v1 (S7); `profile.packing` terisi; tidak ada kunci `split`/`tune` dan tidak ada nilai `"transfer"` di data profil. Impor di korpus {da}: 200 `ok:true`.
- Bug yang ditangkap: `held_out` diisi `{n_items:5,…}` dari butir akta; `n_items:0` dengan rata-rata 0; label "transfer" bocor sebagai nilai data (H-059); akta dipaksa punya `SplitRecord`.

### S11 — Laporan held-out UU PT
- Masukan: fixture S8 (h1–h4, t1, t2, setting `P1`) ke pembangun laporan (A18), `family = uupt`.
- Langkah hitung: baris = hanya h1–h4 (t1, t2 tidak muncul). h1 `10 of 10` chars, `4 of 8` tokens, RR 1, Recall@K 1,0; h2 `15 of 20`, `2 of 10`, RR 0,5, Recall@K 0,5; h3 `0 of 5`, `0 of 6`, RR 0, Recall@K 0,0; h4 catatan `no gold (must abstain)`, kolom recall/precision/RR/Recall@K kosong (null, bukan 0). Per asal (butir bergold): operator {h1,h2}: recall `(1+0,75)/2 = 0,875`, precision `(0,5+0,2)/2 = 0,35`; spark_disetujui {h3}: 0,0 dan 0,0. Per mode: literal {h1 bergold, h4 tanpa gold}: recall 1,0, precision 0,5; parafrase {h2,h3}: recall `(0,75+0)/2 = 0,375`, precision `(0,2+0)/2 = 0,1`. Butir `operator` di held-out = h1, h2, h4 = 3.
