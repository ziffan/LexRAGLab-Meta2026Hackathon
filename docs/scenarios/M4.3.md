## Definisi bersama

**Tokenizer mainan `toy-ws` versi `1`.** Token = deretan maksimal karakter bukan-spasi; offset `[start,end)` code point. Test nyata memakai tokenizer fake/injeksi dengan perilaku ini, bukan tokenizer H-014.

**Dokumen UU PT mainan** (`family = uupt`, teks bersih = teks mentah, tanpa anotasi):
- `d1` = `a0 a1 a2 a3 a4 a5 a6 a7 a8 a9` (10 token, panjang 29). Token ke-i (mulai 0) menempati `[3i, 3i+2)`. Potongan token i..j = `[3i, 3j+2)`.
- `d2` = `b0 b1 b2 b3 b4 b5` (6 token, panjang 17), aturan offset sama.
- `d1x` = `d1` dengan token `a9` diganti `x9` (panjang tetap 29, SHA-256 mentah lain, offset potongan sama persis). `d1n` = `d1` plus satu `\n` di akhir (panjang 30). `d3` = dokumen UU PT ketiga sembarang. `da2` = akta kedua sembarang; `da'` = `da` dengan `Aa bb.` diganti `Xx bb.` (panjang 45).
- SHA-256 mentah `H(d)` dan `clean_sha256` dihitung test dengan `hashlib` atas byte UTF-8; skenario hanya menyatakan sama/beda.

**Dokumen UU PT multibyte `d4`** (R2-1; `family = uupt`, teks bersih ≠ mentah). Berkas mentah (UTF-8) = `Café ab[^1] c› d` (16 code point); pemuat suntikan membuang penanda `[^1]` sebagai anotasi (H-046) sehingga teks bersih = `Café ab c› d`: 12 code point, 15 byte UTF-8 (`é` 2 byte, `›` U+203A 3 byte). Token `toy-ws`: `Café` `[0,4)`, `ab` `[5,7)`, `c›` `[8,10)`, `d` `[11,12)`. SHA-256 mentah ≠ `clean_sha256`. Semua offset dan `D[start:end)` dihitung atas code point teks bersih.

**Dokumen akta mainan** (`family = akta`), `da`, panjang 45, `⏎` = `\n`:
`Pasal 1⏎Aa bb.⏎Pasal 2⏎Cc dd.⏎Pasal 3⏎Ee ff.⏎` — `Pasal 1⏎` = `[0,8)`, `Aa bb.⏎` = `[8,15)`, `Pasal 2⏎` = `[15,23)`, `Cc dd.⏎` = `[23,30)`, `Pasal 3⏎` = `[30,38)`, `Ee ff.⏎` = `[38,45)`.

## Skenario

### S1 — Round-trip UU PT: potongan identik
- Masukan: ekspor profil `P1` (W7) untuk korpus {d1, d2}; salin respons; impor (W8) pada korpus yang sama.
- Langkah hitung: bangun ulang dari `profile.setting` → d1 `[0,11) [9,20) [18,29)`, d2 `[0,11) [9,17)` = 5 potongan, urutan seperti definisi `P1`. `chunk_id` tiap potongan sama dengan yang dibangun saat ekspor (sama `doc_id`, offset, `chunker_key`). `chunk_set_hash` bangun ulang = `profile.chunk_set_hash` = hash dari 5 `chunk_id` tadi.
- Jawaban yang diharapkan: `profile.chunk_set_hash` = golden di atas; HTTP 200 `{"ok": true, "chunk_set_hash_matches": true}`; daftar `(doc_id,start,end)` hasil bangun ulang sama persis (5 elemen); `profile.corpus_hash` = `corpus_hash` yang dihitung dari {d1,d2}. **Golden** (dihitung independen dengan `hashlib` dan rumus di Definisi, lalu dicocokkan dengan `make_chunker_key`/`make_chunk_id`): `chunker_key(P1)` = `1a0bc532b2e0296515946fd1379cf412ddd7ca89ec8153616aad88e0ab96a617`. Pasangan `(chunk_id, teks)` terurut: `(6d0748826fa49265c0d3ef8b9eea3db3a80ed323c59ba20cb5d48b91df9e499d, "a0 a1 a2 a3")` d1 `[0,11)`; `(5d9ae131daa7bf53b5be7135e86813ddb3b0d4985adbb4883dbf27200664756c, "a3 a4 a5 a6")` d1 `[9,20)`; `(56e4babff70cdef0f90c47ce010de6cf381f6a6cbbe344d2bd3a3359788c144c, "a6 a7 a8 a9")` d1 `[18,29)`; `(806c2c424c1e2a93985456a0e9e7b12d2a311388f878ac9a1aa9205428002aa6, "b0 b1 b2 b3")` d2 `[0,11)`; `(52e927bece9c8817cca2d367e87373440bbd860ae5a5ebc41ee4bdb875969816, "b3 b4 b5")` d2 `[9,17)`. Hash potongan profil `P1` = `81c2d2adc46f0c674c36086a59e942749aeadd28ea69010c42dcebd57971fdcb`; `profile.chunk_set_hash` harus persis nilai ini (berlaku bila operator memilih A2 = X; bila Y, golden dihitung ulang).
- Variasi: (i) bangun ulang di dua proses terpisah dengan `PYTHONHASHSEED=1` dan `=2` memberi hash potongan profil yang sama. (ii) Urutan: fake mengembalikan potongan tiap dokumen dalam urutan terbalik dan korpus dimuat `[d2, d1]` → hash sama dengan (i) dan dengan ekspor semula (A21). (iii) Pembanding "run asal" (A20): `profile.chunk_set_hash` = nilai fungsi yang sama atas chunks setting `P1` dari jalur grid/`runs/chunks/`.
- Bug yang ditangkap: hash memuat `created_at` atau `run_id`; hash bergantung urutan dict/set, seed hash Python, atau urutan keluaran chunker/urutan muat (variasi ii); fungsi hash profil beda dari jalur grid sehingga "sama dengan run asal" tak pernah benar (iii); bangun ulang memakai parameter default config alih-alih `profile.setting`; offset dihitung dalam token alih-alih code point.

### S2 — Profil mandiri terhadap perubahan config
- Masukan: ekspor `P1`. Ubah config suntikan: `config/grid.fixed_size` jadi 512/64, sehingga `config_hash` aktif ≠ `profile.config_hash`. Impor.
- Langkah hitung: bangun ulang memakai `setting` 4/1 dari profil → 5 potongan yang sama dengan S1.
- Jawaban yang diharapkan: 200 `{ok:true, chunk_set_hash_matches:true}`; tidak ada 409.
- Bug yang ditangkap: bangun ulang dari config aktif (hash beda); menolak impor karena `config_hash` beda.

### S3 — Hash potongan profil peka terhadap offset, parameter, dan isi teks; pemalsuan terdeteksi
- Masukan: (a) profil `P1` dan `P2` pada korpus yang sama. (b) profil `P1` yang `setting.overlap_tokens` diubah 1 → 2 (dan `setting_id` dihitung ulang agar lolos validasi) dengan `chunk_set_hash` tetap milik `P1`. (c) profil `P1` yang `chunk_set_hash`-nya diubah satu karakter heks. (d) pemalsuan korpus: korpus aktif {d1x, d2}; profil `P1` yang `corpus_hash` dan `clean_sha256`-nya dipalsukan menjadi nilai korpus {d1x, d2}, `chunk_set_hash` tetap asli milik {d1, d2}.
- Langkah hitung: (a) `P1` 5 potongan, `P2` 6 potongan: `setting_id` dan `chunk_set_hash` berbeda. (b) bangun ulang dengan overlap 2 → 6 potongan → hash `P2` ≠ klaim `P1`. (c) bangun ulang 5 potongan benar → hash ≠ klaim rusak. (d) cek korpus lolos (nilai dipalsukan cocok); offset dan `chunk_id` hasil bangun ulang identik dengan `P1` (d1x sama panjang), tetapi potongan ketiga d1 `[18,29)` berteks `a6 a7 a8 x9` ≠ `a6 a7 a8 a9` → hash potongan profil (A2) beda.
- Jawaban yang diharapkan: (a) dua `chunk_set_hash` berbeda. (b), (c), dan (d): HTTP 200 `{"ok": false, "chunk_set_hash_matches": false}` (A5); bukan 409, bukan 500, bukan `ok:true`.
- Bug yang ditangkap: impor menyalin hash klaim ke hasil dan melaporkan cocok; hash dihitung dari `setting` saja, bukan dari potongan; hanya membandingkan jumlah potongan; 500 saat tak cocok; hash atas `chunk_id`/offset saja yang meloloskan korpus beda isi dengan offset sama (d, A2 opsi Z).

### S4 — Korpus beda ditolak dengan pesan jelas
- Masukan: profil `P1` (dari {d1,d2}); korpus aktif, satu uji per varian: (a) {d1x, d2}; (b) {d1n, d2}; (c) {d1} (d2 hilang); (d) {d1, d2, d3}; (e) seperti (a) **dan** `profile.chunk_set_hash` dirusak.
- Langkah hitung: `corpus_hash` aktif (a)–(e) ≠ `profile.corpus_hash` (pasangan `(doc_id, sha256)` atau himpunan dokumen berbeda).
- Jawaban yang diharapkan: semua varian HTTP 409, `error.code = "hash_mismatch"`, `error.message` memuat kalimat persis `Profile corpus hash does not match loaded corpus` dan 12 heks pertama `corpus_hash` profil serta `corpus_hash` aktif; tanpa stack trace. Chunker fake 0 panggilan; `profiles/` dan `runs/` tak berubah. Varian (e) tetap 409, bukan `ok:false`.
- Bug yang ditangkap: menolak hanya bila jumlah dokumen beda ((a),(b) lolos); hash dari `char_count`; membangun ulang lalu 200 `ok:false` alih-alih menolak; urutan cek terbalik (e); pesan generik tanpa hash; pesan berisi stack trace.
