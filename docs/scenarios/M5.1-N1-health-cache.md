# Spec M5.1-N1 — `/api/health` cepat saat muat awal (indeks record inkremental)

Status: draf, menunggu pemeriksa L3. Mandat: putusan operator 17 butir 2; temuan N-1 (dan N-3) cek remedi UX M5.1. Bukan slice Tier 1; skenario di bawah bukan butir evaluasi (H-006). Tanpa panggilan model.

## 1. Penyebab terukur (worktree, 14.249 berkas `runs/spark/records/` 61 MB + 11 amplop `runs/grid/`, 30 Okt)

| Ukuran (proses baru, `TestClient`) | Detik |
|---|---|
| `/api/health` panggilan pertama / kedua / ketiga (berurutan) | 2,674 / 0,946 / 0,922 |
| `/api/runs?limit=500` berurutan | 0,942 / 0,882 |
| Muat awal UI: 3x health + 1x runs bersamaan (App, Evidence, RunLog) — wall, ronde 1 / 2 | 5,402 / 6,084 |
| Rincian satu pemindaian: `read_bytes` 14k berkas / `json.loads` / `RunRecord.from_dict` | 0,621 / 0,112 / 0,080 |
| `os.scandir` + `stat` 14k berkas | 0,013 |
| `is_off_pin` atas 14k record | 0,034 |

Penyebab: setiap R1 dan R6 membaca ulang SEMUA berkas record (open+read per berkas mendominasi), dan frontend menembak health tiga kali plus R6 sekaligus saat muat; empat pemindaian penuh berebut GIL = 5-6 detik. Selama itu header menampilkan `n/a` (null diperlakukan "tidak terbaca") dan "Run live" nonaktif dengan alasan statis.

## 2. Desain

Backend (`backend/spark/store.py`, `backend/api/routers/system.py`, `backend/api/app.py`):
1. **Indeks direktori inkremental** per direktori (di-resolve): peta `nama berkas -> (st_mtime_ns, st_size, hasil parse)`. Tiap pemanggilan: `os.scandir` (13 ms), parse ulang hanya berkas baru atau yang `(mtime_ns, size)`-nya berubah, buang yang hilang; hasil diurutkan menurut nama (= urutan `sorted(glob("*.json"))` sekarang). Satu `threading.Lock` per direktori: pemanggil serentak menunggu satu pemindaian, bukan menggandakannya.
2. Semantik galat sama: record rusak -> `ValueError` (tidak di-cache sebagai sah; dicoba lagi pada panggilan berikut). Grid: amplop tanpa record/rusak dilewati (sama dengan `grid_records`).
3. `load_records` publik tetap seperti sekarang (dipakai Ledger/gate untuk keputusan biaya; tidak disentuh). Varian ber-indeks `load_records_indexed` dipakai HANYA oleh R1 (`cost_fields`) dan R6 (`all_records`). Agregat dihitung dari record ter-indeks tiap permintaan (~50-80 ms), tanpa memo agregat kedua (lebih sedikit keadaan basi).
4. **Pemanasan**: lifespan `create_app` memulai thread daemon yang memanggil indeks records + grid sekali. Health yang datang sebelum pemanasan selesai menunggu lock lalu memakai hasilnya (tidak lebih lambat dari sekarang, tidak pernah angka parsial).
5. Kontrak R1/R6 tidak berubah (bidang, tipe, null-semantics). Tanpa dependensi, tanpa database (H-013).

Frontend (`frontend/src/api.ts`, `components/Header.tsx`, `components/Evidence.tsx`, `components/RunLog.tsx`, `lib/evidence.ts`):
6. `fetchHealth` berbagi satu promise selama permintaan masih berjalan (3 pemanggil -> 1 request); setelah selesai, pemanggilan berikut menembak ulang (tidak basi).
7. Header: selama health belum selesai, Model dan "Run cost (main results)" menampilkan `loading…`; `n/a` hanya bila health selesai dan nilainya null/galat.
8. "Run live": selama health belum selesai, nonaktif dengan alasan jujur "Checking model availability…" (bukan alasan mode statis). Ketersediaan model hanya diketahui dari R1; dengan (1)+(6) health hangat < 1 s sehingga jendela ini pendek.
9. RunLog (N-3): selama health belum selesai, keterangan agregat per peran berbunyi loading, bukan "latest N runs only".

## 3. Invariant

- I1 Identitas: untuk store yang sama, keluaran `cost_fields` dan R6 lewat indeks == jalur tanpa indeks (`store.load_records` + `grid_records` lama), dibandingkan sebagai byte JSON kanonik.
- I2 Tidak basi: setelah record baru disimpan (`save_record`, di proses yang sama atau proses lain), dihapus, atau ditulis ulang, panggilan berikut mencerminkannya.
- I3 Galat: record rusak -> bidang biaya R1 null dan R6 500 seperti sekarang; setelah diperbaiki, pulih.
- I4 Replay/statis: mode replay dan `health.json` ekspor statis tidak berubah (ekspor memakai R1 lewat TestClient; nilai identik oleh I1, jadi berkas statis tidak perlu diulang).
- I5 Tanpa dependensi baru, tanpa database, `config/` dan `runs/` tidak disentuh. Uang tetap integer micro-USD.
- Asumsi I2: penulisan record memakai `os.replace` (berkas baru -> `mtime_ns` berubah); penulisan ulang dengan `mtime_ns` DAN ukuran identik tidak terdeteksi (tidak terjadi di jalur tulis repo).
