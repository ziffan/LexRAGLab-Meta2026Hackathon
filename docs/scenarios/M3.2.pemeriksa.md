## Kesesuaian spec
- Kriteria 1 M3.2 ("lebih sedikit teks sumber"): skenario melemah ke `<=` dengan `=` di B=8 dan 21 (A8). Matematis benar untuk `stop` (prefiks on adalah subhimpunan prefiks off). **Tidak benar untuk `skip`** bila header berbeda antar potongan: C=(a: sumber 3, header 5), (b: sumber 4, header 1), B=6, `skip` -> off sumber 3, on sumber 4. A8 harus dibatasi ke `stop` (default); S10 memakai `skip` jadi jangan ada assert invarian di sana. Operator perlu mengonfirmasi pelemahan `<` -> `<=`.
- Kriteria 2 (span di teks sumber): S6, S12 cukup; screenshot di luar skenario (A13).
- EVAL-SPEC §3 dan §5 dipatuhi (cost = tok(hdr)+tok(teks); header tidak gold). Rank = posisi di `P` (§6) dipakai konsisten.
- A1 (frontier gabungan) sebenarnya sudah diputus oleh DATA-CONTRACTS §10: `Frontier` keyed `(family, split, budget_tokens)` tanpa `header_b`, dan dominasi §9 tidak mengenal deret. Bukan pilihan operator; alternatif per deret bertentangan dengan kontrak. Cukup tulis sebagai "mengikuti §10".
- A3 diputus oleh EVAL-SPEC §2 (satu tokenizer lokal untuk semua `tok(.)`) dan §5; A11 diputus oleh H-004/EVAL-SPEC §3. Bukan pilihan, hanya konfirmasi.
- A6: MILESTONES (tabel pemicu baris 4) dan SPARK-ROLES §3 hanya mengatakan "hanya setting di frontier"; frontier mana (tune, header-off) memang belum ditulis spec, jadi A6 sah sebagai usulan. Kutipan "H-049 butir 6" tidak ditemukan di docs repo (EVAL-SPEC §8 tidak bernomor butir 6); verifikasi atau hapus.
- `config/grid.toml` `header_b = [false, true]` dan `expand.py` sudah menghasilkan kembaran untuk semua setting (A15 M1.4). Skenario harus menyatakan lapisan mana yang menyaring menurut `scope`.
- S12 melanggar perilaku backend BM25 nyata (B1).
- A9: `ItemMetrics` tanpa token header; turunan `retrieved - Σ tok(sumber P)` bisa dipenuhi test; tidak ada konflik.

## Temuan putaran 2
- **P-A PERLU-PERBAIKAN — S9 (c)/(d) tidak menggigit pada `granularity`; dan `Setting` (§10) tidak memuat granularitas.** `granularity` hanya field metadata `HeaderB`; `chunk_id` memuat `chunker_key` (chunker, parameter, versi skema), bukan granularitas B. Jadi SP dan SA harus dibedakan oleh `chunker_key`, tetapi `Setting` hanya punya `chunker` (3 nilai), `chunk_size_tokens`, `schema_version`; "struktur per pasal" vs "struktur per ayat" tidak dapat dinyatakan di §10. Skenario harus (1) menyatakan bagaimana kedua chunker dibedakan (parameter chunker di `chunker_key`, mis. `unit=pasal`/`unit=ayat` di config chunking), dan (2) menambah kasus yang menegakkan `granularity`: store berisi `chunk_id` yang sama dengan `granularity` berbeda dari config, harapan galat "granularitas tidak cocok" (atau, bila tidak dicek, hapus klaim "granularitas diabaikan" dari daftar bug S9).
- **P-B PERLU-PERBAIKAN — S4/A4 "kegagalan dicatat" tak punya tempat yang dapat diuji.** `RunRecord.status/error` satu per run. Tentukan tempat: daftar `failed_settings: [{setting_id, code, message}]` di RunRecord (perlu perubahan kontrak, minta operator) atau berkas hasil grid. Tanpa itu asersi "dicatat" mengambang.
- **P-C PERLU-PERBAIKAN — S8 tidak menguji run ulang dengan deret on yang sudah ada dari run `scope=all`.** Tambahkan: setelah `scope=all` (4 kembaran on tersimpan), `scope=frontier_only` pada data yang sama harus tetap mengeksekusi (atau membaca dari cache, S13) hanya {s1+, s2+, s4+} dan frontier-only dihitung dari deret off, bukan dari frontier gabungan lama (A1) yang sudah memuat on. Kalau frontier gabungan lama dipakai, s3 bisa ikut/tersingkir secara berbeda.
- CATATAN 1: S8 hanya satu anggaran; Setting memuat `budget_tokens` jadi per-anggaran sebagian terjaga oleh desain, tetapi tambah dua anggaran bila murah.
