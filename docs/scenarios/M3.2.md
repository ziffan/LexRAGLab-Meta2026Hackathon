## Lingkup dan konvensi (tidak mengulang M1.2)

M3.2 memakai kalkulator metrik M1.2 apa adanya (di luar scope: "dipakai, tidak diubah"). Aturan pengemasan, definisi token gold, dan truncate dengan `r ≤ 0` sudah diuji di M1.2 (S4, S17) dan tidak diulang. Yang diuji di sini adalah apa yang baru di M3.2:

1. header B menjadi sumbu grid: setiap setting punya kembaran `header_b = true/false` dan hasilnya membentuk dua deret;
2. `hdr(c)` berasal dari HeaderB yang benar (kunci, validitas, granularitas, tokenisasi), lalu masuk akuntansi anggaran yang sama;
3. pada anggaran sama, setting berheader membawa lebih sedikit teks sumber, dan itu terukur;
4. offset dan gold selalu pada teks sumber, bukan teks berheader;
5. cakupan "hanya frontier" (H-017) dan kunci cache.

**Tokenizer mainan `toy-ws` versi `1`** dan **dokumen mainan T** (20 token dua huruf `a0 … b9`, token ke-i di `[3i, 3i+2)`, panjang 59) sama dengan `docs/scenarios/M1.2.md` ("Definisi bersama"). **Dokumen mainan U** dan peta alamatnya juga sama dengan M1.2. Test nyata memakai tokenizer fake/injeksi dengan perilaku persis itu untuk teks sumber **dan** teks header; header ditokenisasi sebagai string tanpa offset dokumen. `tok(header)` = jumlah deretan maksimal karakter bukan-spasi (spasi, newline, tab = pemisah), termasuk header berspasi ganda.

**Potongan baku T:** c1 `[0,11)` tok 4; c2 `[12,26)` tok 5; c3 `[27,32)` tok 2; c4 `[33,41)` tok 3 (seperti M1.2).

**Header baku untuk T (dipakai S1, S2, S10):** `h(c1)="H1 H2"` (2), `h(c2)="H3"` (1), `h(c3)="H4 H5 H6"` (3), `h(c4)="H7"` (1). Biaya `cost = tok(hdr)+tok(teks)`: header off 4, 5, 2, 3; header on 6, 6, 5, 4.

Kecuali disebut lain: packing `stop`, `tune` split, `HeaderB` sudah tersimpan di store untuk semua `chunk_id` yang dipakai, lolos validitas (S5), dan retrieval dilewati: ranking `C` diberikan sebagai masukan (retrieval palsu), kecuali S12. Semua pecahan eksak.

## Asumsi dan pilihan yang perlu disetujui operator

1. **A1 — dipindah ke "Sudah diputus spec"** (frontier gabungan mengikuti DATA-CONTRACTS §10). Alternatif per deret dihapus karena bertentangan dengan kontrak.
2. **A2 — granularitas B (H-038): kunci header.** Kontrak berlaku: `HeaderB.chunk_id` "harus sama dengan potongan yang diminta" (DATA-CONTRACTS §7) dan satu potongan per panggilan (SPARK-ROLES §3). Dipilih (S9 utama): header **per `chunk_id`**; `granularity` (`pasal`/`ayat`) menentukan **potongan mana yang diminta ke B**, yaitu potongan struktur pada granularitas itu. Konsekuensi yang diuji: header-on hanya tersedia untuk setting yang `chunk_id`-nya ada di store; setting lain (granularitas lain) yang meminta header-on tidak pernah meminjam header, dan mendapat galat A4. Potongan `fixed_size` (H-062) dan `structure_schema` mengikuti aturan yang sama: header per `chunk_id`, B diminta untuk potongan setting itu (A16). **Diputus operator (H-069): per `chunk_id`.** Alternatif per unit (S9-alt) ditolak; S9-alt dipertahankan hanya sebagai catatan dan TIDAK DIJALANKAN.
3. **A3 — dipindah ke "Sudah diputus spec".** Tersisa sebagai pilihan: `tokens_local` yang tidak cocok dengan hitung ulang diabaikan atau dicatat sebagai peringatan (tidak dikunci); skenario hanya melarang pengaruhnya pada anggaran (S3).
4. **A4 — header hilang atau tidak sah pada setting `header_b=true`.** Dipilih: **galat jelas** (jenis khusus; pesan memuat `chunk_id` dan `setting_id`) bila **sebarang** potongan di himpunan potongan setting (bukan hanya di `P`; indeks on membutuhkan semuanya) tidak punya header; header yang tokennya 0 (`""` atau hanya spasi/tab/newline) juga **tidak sah** (jenis galat sama, pesan berbeda), karena header kosong membuat "on" diam-diam sama dengan "off". Efek: setting itu gagal dan dicatat; run lanjut untuk setting lain; tidak ada `GridPoint`; tidak ada cache sah untuk setting itu. Alternatif: header kosong sah dengan biaya 0 (S3 varian c menunjukkan angkanya); run berhenti total pada galat pertama. S3, S4.
5. **A5 — validitas header.** `HeaderB` tidak memuat `clean_sha256` atau `corpus_hash`; keduanya ada di `RunRecord` run `spark_b`. Dipilih: header dipakai hanya bila `chunk_id` cocok (termasuk `chunker_key`) **dan** run B yang menghasilkannya punya `clean_sha256` (H-046) sama dengan run grid; selain itu ditolak. `chunk_id` sendiri tidak memuat `clean_sha256` (§3), jadi cek ini perlu. Alternatif: tambah field di `HeaderB`. S5.
6. **A6 — cakupan "hanya frontier" (H-017, H-038).** Spec hanya berkata "setting di frontier"; frontier mana tidak ditulis. Dipilih: header-on dihitung hanya untuk setting yang ada di **frontier tune header-off** per anggaran; held-out tidak boleh memengaruhi himpunan itu (EVAL-SPEC §8 butir 6, "butir held-out dilarang dipakai untuk memilih setting"). **Lapisan penyaring:** `config/grid.toml` memuat `header_b = [false, true]` dan ekspansi grid (`expand`) tetap menghasilkan **semua kembaran** (produk Cartesian penuh, M1.4 A15); penyaring `scope = frontier_only` ada di **runner grid** (`backend/`, M3.2), yang menjalankan deret off dulu, lalu hanya mengeksekusi kembaran header-on dari titik frontier tune; kembaran lain tidak dieksekusi dan tidak menghasilkan `GridPoint`. Alternatif: `scope` diberikan ke `expand` sehingga kembaran itu tak pernah dibentuk; semua setting (`scope = all`). S8.
7. **A7 — teks yang diindeks.** Dipilih: setting header-on mengindeks `header + "\n" + teks sumber` (header dulu); header-off mengindeks teks sumber **persis**, tanpa jejak header. Test hanya mengunci: off = sumber persis; on memuat header dan teks sumber; offset tidak bergeser (S6, S12). Format pemisah dan urutan tidak dikunci. Catatan: untuk embedder, header di depan membuat potongan lebih sering terpotong `max_seq_length` (`RunRecord.embedder.n_truncated`); ditangani di Tier 2.
8. **A8 — makna "lebih sedikit teks sumber" (operator mengonfirmasi pelemahan `<` menjadi `≤`).** Hanya untuk `packing = stop` (default, H-033 a) dan ranking `C` sama untuk kedua deret: token sumber di `P` header-on **≤** header-off pada setiap anggaran, dan **<** pada anggaran di mana header menyebabkan minimal satu potongan tersingkir (S2); sama pada anggaran lain (S2: B=8, B=21). Alasan: pada `stop`, prefiks yang muat di on adalah prefiks dari yang muat di off. **Tidak berlaku untuk `skip`:** S2b adalah contoh tandingan (on membawa 4 token sumber, off 3). Juga tidak berlaku bila `C` berbeda antar deret (retrieval header-on mengubah peringkat, S14). `truncate` tidak diklaim. Alternatif lebih ketat (`<` di semua B) tidak benar secara matematis.
9. **A9 — rincian token header per butir.** `ItemMetrics` tidak memuat jumlah token header; skenario menurunkannya sebagai `retrieved_tokens − Σ tok(teks sumber P)` dan meminta test memeriksa hasil itu. Usulan: tambah `header_tokens: int` (nullable) di `ItemMetrics` supaya UI bisa menampilkan hitungan mentah. Operator memutus; skenario berlaku tanpa field ini.
10. **A10 — identitas header di kunci cache grid.** Kunci grid (`ARCHITECTURE` §8) `hash(clean_sha256, config_hash, item_set_hash, split_version)` tidak menyebut header. Dipilih: `config_hash` mencakup **hash isi store header** (kumpulan pasangan `chunk_id` → teks header), granularitas, `prompt_hash` B, model, dan `header_b.scope`; **`run_id` B tidak masuk kunci** (isi header sama dari run berbeda memberi cache hit, S13 R7). Alternatif: komponen kelima di kunci; `run_id` ikut. S13 tidak mengunci apakah deret off ikut dihitung ulang (kunci per run, M1.4 A13); hanya melarang hasil basi.
11. **A11 — dipindah ke "Sudah diputus spec".**
12. **A12 — butir tanpa gold dan `mean_retrieved_tokens`.** Mengikuti M1.2 A8 (rata-rata atas butir bergold); header menambah `retrieved_tokens` butir tanpa gold tetapi butir itu tidak masuk rata-rata. S11.
13. **A13 — cakupan.** Panel frontend (dua deret, catatan "header B computed for frontier settings only") dan pemanggilan Spark B (M3.1) di luar skenario ini; slice tidak ditutup tanpa test Tier 2 untuk payload U2 dan screenshot.
14. **A14 — granularitas dan kontrak (asumsi kontrak).** `Setting` (DATA-CONTRACTS §10) tidak punya field granularitas; granularitas hanya di `config/header_b` dan `HeaderB.granularity`. Dipilih: SP dan SA dibedakan lewat `chunker_key` (hash chunker + parameter + versi skema, §3), sehingga `chunk_id`-nya berbeda; `config_hash` memuat granularitas (A10). Header dipakai hanya bila `chunk_id` cocok **dan** `HeaderB.granularity` sama dengan `config/header_b.granularity` (S9 (e)). Alternatif: tambah field granularitas di `Setting` (ikut `setting_id`); atau hanya `chunk_id` yang diperiksa. Operator memutus; bila field ditambah, S9 dan S13 disesuaikan.
15. **A15 — tempat mencatat kegagalan per setting (A4).** `RunRecord` (§12) hanya punya satu status per run. Diputus (H-069): field baru di `RunRecord` `kind=grid`, `failed_settings: array of {setting_id, reason, chunk_id | null}`, terisi untuk setiap setting yang gagal (tidak ada `GridPoint` untuk setting itu). Alternatif ditolak: satu `RunRecord` per setting; berkas galat terpisah. S4 dan S8 meng-assert isi catatan (`setting_id`, `reason`, `chunk_id`); catatan "dilewati" tidak ada (tidak ada kembaran yang dilewati, A16).
16. **A16 — kembaran header-on untuk `fixed_size` (H-062, H-058; DIPUTUS operator H-069, opsi C).** Dengan A2 (kunci `chunk_id`) dan H-062 (`fixed_size` = jendela tetap lintas Pasal/section; `chunk_id` ikut ukuran/overlap setting), header B untuk potongan `fixed_size` harus diminta ke B; H-058 mengunci header B x 2 untuk semua chunker, jadi kembaran header-on `fixed_size` **berlaku** (bukan dilewati). Aturan: B diminta untuk potongan `fixed_size` setting yang lolos `frontier_only` (A6), satu potongan per panggilan (SPARK-ROLES §3), dengan cache dan proyeksi biaya lebih dulu (gerbang belanja). Setting `fixed_size` di luar frontier tidak diminta headernya (sama dengan setting lain, S8). Header `fixed_size` disimpan per `chunk_id` seperti potongan lain; `structure_schema` memakai aturan yang sama (per `chunk_id`, dibedakan `chunker_key`, A14). Akuntansi anggaran, offset, dan gold tidak berbeda dari potongan struktur (S15). Tetap galat A4 bila header potongan `fixed_size` hilang atau kosong setelah B diminta (S4 (c)); tidak ada pengecualian menurut nama chunker. Pemanggilan Spark B itu sendiri (M3.1) di luar skenario ini (A13); lingkup M3.1 bertambah (MILESTONES). Mengubah kontrak/spec: ya (MILESTONES M3.1/M3.2; UI-SPEC U2 bila kembaran ditampilkan).

## Skenario

### S1 — Anggaran sama: header-on membawa lebih sedikit teks sumber, recall turun
- Masukan: T. `C = (c1, c2, c3, c4)` untuk kedua deret (ranking sama). Header baku T. `B = 11`, stop. `gold_spans = [[15,20)]` (`G={15..19}`, `|G|=5`, token 5 `[15,17)` dan token 6 `[18,20)` di dalam c2).
- Langkah hitung:
  - Header off: biaya 4, 5, 2, 3 → akumulasi 4, 9, 11 (≤ 11, masuk), 14 > 11 stop. `P=(c1,c2,c3)`. Token sumber 4+5+2 = 11, header 0, `retrieved=11`. `c2∩G=[15,20)`=5 → covered 5. Token gold: token 5, 6 → 2. Rank c2 = 2.
  - Header on: biaya 6, 6, 5, 4 → akumulasi 6 (masuk), 12 > 11 stop. `P=(c1)`. Token sumber 4, header 2, `retrieved=6`. covered 0, token gold 0. Tidak ada rank.
- Jawaban yang diharapkan:

| deret | P | token sumber | token header (A9) | retrieved_tokens | span_recall | token_precision | rr | fully_covered |
|---|---|---|---|---|---|---|---|---|
| off | (c1,c2,c3) | 11 | 0 | 11 | 5/5 | 2/11 | 1/2 | true |
| on | (c1) | 4 | 2 | 6 | 0/5 | 0/6 = 0 | 0 | false |

  Token sumber on (4) < off (11); `retrieved_tokens` on (6) ≤ B (11). `Setting` kembar berbeda hanya di `header_b` dan `setting_id`.
- Bug yang ditangkap: header tidak dihitung ke anggaran (on memberi `P=(c1,c2,c3)`, `retrieved` 11 + header 6 = 17 > B, atau hasil on = hasil off); header dihitung tetapi hanya untuk potongan pertama; header on dibuang dari penyebut presisi (0/4 = 0 tidak terdeteksi, tetapi `retrieved=4` salah); `precision` on `null` padahal `retrieved=6`; anggaran header-on diperlebar (`B + Σ header`); setting_id kembar sama.

### S2 — Sapuan anggaran (hanya `packing=stop`): invarian token sumber on ≤ off, tepat sama di dua titik
- Masukan: T, ranking `C=(c1,c2,c3,c4)` sama untuk kedua deret, header baku T, gold dan packing seperti S1. Anggaran `B ∈ {5, 8, 11, 12, 13, 16, 20, 21}`.
- Langkah hitung (akumulasi off: 4, 9, 11, 14; akumulasi on: 6, 12, 17, 21):

| B | off P | sumber/header/ret | span | prec | rr | on P | sumber/header/ret | span | prec | rr |
|---|---|---|---|---|---|---|---|---|---|---|
| 5 | (c1) | 4/0/4 | 0 | 0 | 0 | () | 0/0/0 | 0 | null | 0 |
| 8 | (c1) | 4/0/4 | 0 | 0 | 0 | (c1) | 4/2/6 | 0 | 0 | 0 |
| 11 | (c1,c2,c3) | 11/0/11 | 1 | 2/11 | 1/2 | (c1) | 4/2/6 | 0 | 0 | 0 |
| 12 | (c1,c2,c3) | 11/0/11 | 1 | 2/11 | 1/2 | (c1,c2) | 9/3/12 | 1 | 1/6 | 1/2 |
| 13 | (c1,c2,c3) | 11/0/11 | 1 | 2/11 | 1/2 | (c1,c2) | 9/3/12 | 1 | 1/6 | 1/2 |
| 16 | semua | 14/0/14 | 1 | 1/7 | 1/2 | (c1,c2) | 9/3/12 | 1 | 1/6 | 1/2 |

  (span 1 = 5/5, 0 = 0/5; `rr` tanpa rank = 0. Presisi B=5 on: `retrieved=0` → `null`.)
- Jawaban yang diharapkan: tabel di atas. Invarian yang di-assert (hanya untuk `stop`, A8): untuk semua B, token sumber on ≤ off dan `retrieved_tokens` on ≤ B; sumber on < off pada B ∈ {5, 11, 12, 13, 16, 20}; sama (4 = 4 dan 14 = 14) pada B ∈ {8, 21} (A8). Recall on mencapai 1 baru di B=12, tepat saat akumulasi = B (off di B=11).
- Bug yang ditangkap: header ditambahkan sesudah pengemasan (retrieved on di B=11 = 11+6 = 17 > B, atau `P` on = `P` off di setiap B); `<` menggantikan `≤` pada akumulasi berheader (B=12: c2 ditolak padahal 12 ≤ 12, `P=(c1)`); invarian hanya ditegakkan pada satu B; biaya header dihitung untuk seluruh ranking dan bukan potongan yang masuk; `retrieved_tokens` melaporkan token sumber saja (B=21 on: 14, bukan 21).

### S2b — Contoh tandingan A8: dengan `skip` token sumber on bisa lebih banyak
- Masukan: T. `C=(c4,c1)` untuk kedua deret, `B=6`, `packing=skip`. Header: c4 `"K1 K2 K3 K4 K5"` (5), c1 `"H1"` (1). c4 `[33,41)` tok 3, c1 `[0,11)` tok 4.
- Langkah hitung: off: c4 biaya 3 (akumulasi 3), c1 biaya 4 → 7 > 6, dilewati. `P=(c4)`, sumber 3, `retrieved=3`. On: c4 biaya 5+3 = 8 > 6, dilewati (akumulasi tetap 0); c1 biaya 1+4 = 5 ≤ 6. `P=(c1)`, sumber 4, header 1, `retrieved=5`.
- Jawaban yang diharapkan: token sumber off 3, on 4 (on > off); `retrieved_tokens` on 5 ≤ 6. Test **tidak** meng-assert invarian "on ≤ off" untuk `skip` (juga tidak di S10); ia hanya meng-assert angka ini.
- Bug yang ditangkap: implementasi atau test yang menegakkan invarian sumber-on ≤ sumber-off secara umum (melanggar `skip`); `skip` yang menghentikan pengemasan setelah lompatan pertama (on akan `P=()`).

### S3 — Biaya header dari teks dengan tokenizer run, bukan `tokens_local` atau `usage`
- Masukan: T. `C=(c1,c2)`, `B=12`, stop. `gold_spans=[[0,11)]` (`|G|=11`). HeaderB tersimpan:
  - c1: `header = "H1  H2"` (dua spasi di antara), `tokens_local = 99` (basi), `usage_input_tokens` run asal 1500.
  - c2: `header = "\nH3\n"` (newline di tepi), `tokens_local = 0` (basi).
- Langkah hitung: `tok("H1  H2") = 2`, `tok("\nH3\n") = 1` (A3). `cost(c1)=2+4=6`, `cost(c2)=1+5=6`; akumulasi 6, 12 ≤ 12. `P=(c1,c2)`. covered = `c1∩G` = 11; c2 tak beririsan. Token gold: token 0–3 → 4. `retrieved=12` (sumber 9 + header 3). Rank 1.
- Jawaban yang diharapkan: `P=(c1,c2)`, `retrieved_tokens=12`, `span_recall=11/11=1`, `gold_tokens_retrieved=4`, `token_precision=4/12=1/3`, `rr=1`, `fully_covered=true`.
- Varian (b), tokenizer run kedua `toy-2` versi `1` (hanya untuk biaya; token = `ceil(banyak code point / 2)` dari string tanpa strip, tanpa offset token, jadi presisi tidak di-assert): `tok("H1  H2")=3`, `tok("\nH3\n")=2`, `tok("a0 a1 a2 a3")=6`, `tok("a4 a5 a6 a7 a8")=7`. `B=17`, `C=(c1,c2)`, stop. Biaya c1 = 3+6 = 9 (≤ 17), c2 = 2+7 = 9 → 18 > 17 stop. `P=(c1)`, `retrieved_tokens=9`, `span_recall=11/11`, `rr=1`. Tokenizer fake memakai spy: semua pemanggilan `tok` untuk biaya header menerima **string header saja** (`"H1  H2"`, `"\nH3\n"`), tidak pernah `header + "\n" + teks`, dan hanya tokenizer injeksi run yang dipanggil.
- Varian (c), tab dan header tak sah (A4): header `"H1\tH2"` → `tok=2` (tab pemisah). Header `""` dan `"  \n"` → token 0: galat "header tidak sah" (A4); bila operator memilih alternatif (biaya 0 sah), `cost = 0 + tok(teks)` dan hasilnya sama dengan header off untuk potongan itu.
- Bug yang ditangkap (tambahan): biaya header dengan `len(header.split())` atau tokenizer lain yang kebetulan sama pada `toy-ws` (varian b: c2 ikut masuk, `P=(c1,c2)`, `retrieved=16` ≠ 9); header dan teks digabung dulu lalu ditokenisasi; tab bukan pemisah; header kosong/whitespace-saja lolos dan menghasilkan on = off diam-diam.
- Bug yang ditangkap (S3 utama): memakai `tokens_local` (c1 cost 103 → `P=()`; atau 0 untuk c2 → total berbeda); memecah dengan satu spasi (`"H1  H2".split(" ")` = 3 → cost 7, akumulasi 13 > 12, `P=(c1)`); `strip` salah sehingga `"\nH3\n"` = 0 atau 2; memakai `usage` Spark sebagai biaya header; tokenizer header berbeda dari tokenizer sumber.

### S13 — Kunci cache grid mencakup isi header (A10)
- Masukan: pipeline palsu dengan penghitung panggilan. Tujuh run berurutan pada konfigurasi grid yang sama kecuali yang disebut:

  3. R3: `prompt_hash=p2` dan isi store header baru `e2`.
  4. R4: granularitas `ayat`.
  5. R5: `scope=frontier_only`.
  6. R6: identik dengan R1 lagi.
  7. R7: isi store header **persis `e1`** tetapi `run_id` B baru `b2` (A10: `run_id` tidak masuk kunci).
- Hitung: hitung pemanggilan pipeline hitung-metrik untuk deret on.
- Jawaban yang diharapkan: R1 menghitung (>0 panggilan); R2 tidak ada panggilan; R3, R4, R5 masing-masing menghitung deret on baru (hasil R1 tidak dipakai); R6 tidak ada panggilan (R1 tidak tertimpa R3–R5); R7 tidak ada panggilan (cache hit). - Bug yang ditangkap: header tidak masuk kunci (R3–R5 mengembalikan hasil R1 yang basi); kunci memuat waktu atau `run_id` (R2, R6, R7 menghitung ulang); cache tertimpa (R6 mengembalikan hasil R3).

### S14 — Ujung ke ujung: ranking header-on berbeda dari off sampai ke `P` (BM25 nyata, B palsu)
