## Lingkup dan konvensi (tidak mengulang M1.2)

M3.2 memakai kalkulator metrik M1.2 apa adanya (di luar scope: "dipakai, tidak diubah"). Aturan pengemasan, definisi token gold, dan truncate dengan `r ≤ 0` sudah diuji di M1.2 (S4, S17) dan tidak diulang. Yang diuji di sini adalah apa yang baru di M3.2:

1. header B menjadi sumbu grid: setiap setting punya kembaran `header_b = true/false` dan hasilnya membentuk dua deret;
2. `hdr(c)` berasal dari HeaderB yang benar (kunci, validitas, granularitas, tokenisasi), lalu masuk akuntansi anggaran yang sama;
3. pada anggaran sama, setting berheader membawa lebih sedikit teks sumber, dan itu terukur;
4. offset dan gold selalu pada teks sumber, bukan teks berheader;
5. cakupan "hanya frontier" (H-017) dan kunci cache.

**Tokenizer mainan `toy-ws` versi `1`** dan **dokumen mainan T** (20 token dua huruf `a0 … b9`, token ke-i di `[3i, 3i+2)`, panjang 59) sama dengan `docs/scenarios/M1.2.md` ("Definisi bersama"). **Dokumen mainan U** dan peta alamatnya juga sama dengan M1.2. Test nyata memakai tokenizer fake/injeksi dengan perilaku persis itu untuk teks sumber **dan** teks header; header ditokenisasi sebagai string tanpa offset dokumen. `tok(header)` = jumlah deretan maksimal karakter bukan-spasi (spasi, newline, tab = pemisah), termasuk header berspasi ganda.

**Potongan baku T:** c1 `[0,11)` tok 4; c2 `[12,26)` tok 5; c3 `[27,32)` tok 2; c4 `[33,41)` tok 3 (seperti M1.2).

**Header baku untuk T (dipakai S1, S2, S10):** `h(c1)="H1 H2"` (2), `h(c2)="H3"` (1), `h(c3)="H4 H5 H6"` (3), `h(c4)="H7"` (1). Biaya `cost = tok(hdr)+tok(teks)`: header off 4, 5, 2, 3; header on 6, 6, 5, 4.

Kecuali disebut lain: packing `stop`, `tune` split, `HeaderB` sudah tersimpan di store untuk semua `chunk_id` yang dipakai, lolos validitas (S5), dan retrieval dilewati: ranking `C` diberikan sebagai masukan (retrieval palsu), kecuali S12. Semua pecahan eksak.

## Asumsi dan pilihan yang perlu disetujui operator

1. **A1 — satu frontier gabungan atau dua frontier per deret.** Kontrak `Frontier` (§10) satu per `(family, split, budget_tokens)` dan `Setting.header_b` hanya satu sumbu; U2 mewarnai titik per `header_b`. Dipilih: **frontier gabungan** (konsisten dengan M1.4 A9); "dua deret" = partisi titik menurut `header_b`; `dominated` dihitung gabungan, sehingga titik berheader bisa tersingkir oleh titik tanpa header dan sebaliknya. **Alternatif:** dua frontier terpisah, satu per deret. S7 menunjukkan kedua hasil; operator memilih.
2. **A2 — granularitas B (H-038) dan resolusi header per potongan.** Spec: `HeaderB.chunk_id` = potongan yang diminta, `granularity` ∈ `pasal`/`ayat`, tetapi potongan setting bebas (fixed-size melintasi unit). Dipilih: header ditulis **per unit** pada granularitas terpilih (Pasal, atau ayat; Pasal tanpa ayat = satu unit di kedua granularitas); potongan mengambil header **unit pertama** menurut alamat awalnya (`Chunk.address`, "unit pertama dan terakhir"); header yang sama dipakai potongan lain di unit itu dan **biayanya dihitung di setiap potongan** (duplikasi menambah, seperti overlap). **Alternatif:** header per `chunk_id` secara harfiah (granularitas hanya mengatur potongan mana yang ditulis); header gabungan semua unit yang dilintasi; header di-dedup per unit di konteks. S9 bergantung; bila alternatif dipilih, S9 ditulis ulang.
3. **A3 — tokenisasi header.** Biaya header selalu dihitung ulang dari **teks** dengan tokenizer run; `HeaderB.tokens_local` hanya informasi/audit (nilai basi tidak boleh memengaruhi anggaran) dan `usage` Spark tidak pernah dipakai (EVAL-SPEC §2). Alternatif: percaya `tokens_local` bila tokenizer sama; galat bila tak cocok. S3.
4. **A4 — header hilang pada setting `header_b=true`.** Dipilih: **galat jelas** (jenis khusus; pesan memuat `chunk_id` dan `setting_id`), run/setting itu tidak menghasilkan `GridPoint` dan tidak di-cache sebagai sah. Alternatif: header kosong dengan peringatan (membuat perbandingan on/off diam-diam tidak adil). S4.
5. **A5 — validitas header.** `HeaderB` tidak memuat `clean_sha256` atau `corpus_hash`; keduanya ada di `RunRecord` run `spark_b`. Dipilih: header dipakai hanya bila `chunk_id` cocok (termasuk `chunker_key`) **dan** run B yang menghasilkannya punya `clean_sha256` (H-046) sama dengan run grid; selain itu ditolak. `chunk_id` sendiri tidak memuat `clean_sha256` (§3), jadi cek ini perlu. Alternatif: tambah field di `HeaderB`. S5.
6. **A6 — cakupan "hanya frontier" (H-017, H-038).** Dipilih: header-on dihitung hanya untuk setting yang ada di **frontier tune header-off** per anggaran. Held-out tidak boleh memengaruhi himpunan itu (H-049 butir 6). Alternatif: frontier gabungan seluruh grid (tak mungkin, deret on belum ada); semua setting (`scope = all`). S8.
7. **A7 — teks yang diindeks.** Dipilih: setting header-on mengindeks `header + "\n" + teks sumber` (header dulu); header-off mengindeks teks sumber **persis**, tanpa jejak header. Test hanya mengunci: off = sumber persis; on memuat header dan teks sumber; offset tidak bergeser (S6, S12). Format pemisah dan urutan tidak dikunci. Catatan: untuk embedder, header di depan membuat potongan lebih sering terpotong `max_seq_length` (`RunRecord.embedder.n_truncated`); ditangani di Tier 2.
8. **A8 — makna "lebih sedikit teks sumber".** Dengan ranking sama dan header ≥ 1 token, token sumber di `P` header-on **≤** header-off pada setiap anggaran, dan **<** pada anggaran di mana header menyebabkan minimal satu potongan tersingkir. Di anggaran lain bisa sama (S2: B=8, B=21). Bila `C` berbeda antar deret (retrieval header-on mengubah peringkat), pernyataan itu tidak berlaku; M3.2 mengujinya dengan ranking sama saja (S1, S2). Alternatif lebih ketat (`<` di semua B) tidak benar secara matematis.
9. **A9 — rincian token header per butir.** `ItemMetrics` tidak memuat jumlah token header; skenario menurunkannya sebagai `retrieved_tokens − Σ tok(teks sumber P)` dan meminta test memeriksa hasil itu. Usulan: tambah `header_tokens: int` (nullable) di `ItemMetrics` supaya UI bisa menampilkan hitungan mentah. Operator memutus; skenario berlaku tanpa field ini.
10. **A10 — identitas header di kunci cache grid.** Kunci grid (`ARCHITECTURE` §8) `hash(clean_sha256, config_hash, item_set_hash, split_version)` tidak menyebut header. Dipilih: `config_hash` harus mencakup identitas set header (granularitas, `prompt_hash` B, `run_id`/hash isi store header, model, cakupan `header_b.scope`) sehingga tiap komponen mengubah kunci. Alternatif: komponen kelima di kunci. S13 tidak mengunci apakah deret off ikut dihitung ulang (kunci per run, M1.4 A13); hanya melarang hasil basi.
11. **A11 — anggaran header.** Anggaran `B` sama persis untuk kedua deret; header dalam `B`, bukan tambahan di luar `B` (H-004, EVAL-SPEC §3). Alternatif "header di luar anggaran" ditolak spec.
12. **A12 — butir tanpa gold dan `mean_retrieved_tokens`.** Mengikuti M1.2 A8 (rata-rata atas butir bergold); header menambah `retrieved_tokens` butir tanpa gold tetapi butir itu tidak masuk rata-rata. S11.
13. **A13 — cakupan.** Panel frontend (dua deret, catatan "header B computed for frontier settings only") dan pemanggilan Spark B (M3.1) di luar skenario ini; slice tidak ditutup tanpa test Tier 2 untuk payload U2 dan screenshot.

## Skenario

### S1 — Anggaran sama: header-on membawa lebih sedikit teks sumber, recall turun
- Masukan: T. `C = (c1, c2, c3, c4)` untuk kedua deret (ranking sama). Header baku T. `B = 11`, stop. `gold_spans = [[15,20)]` (`G={15..19}`, `|G|=5`, token 5 `[15,17)` dan token 6 `[18,20)` di dalam c2).
- Langkah hitung:
  - Header off: biaya 4, 5, 2, 3 → akumulasi 4, 9, 11 (≤ 11, masuk), 14 > 11 stop. `P=(c1,c2,c3)`. Token sumber 4+5+2 = 11, header 0, `retrieved=11`. `c2∩G=[15,20)`=5 → covered 5. Token gold: token 5, 6 → 2. Rank c2 = 2.
  - Header on: biaya 6, 6, 5, 4 → akumulasi 6 (masuk), 12 > 11 stop. `P=(c1)`. Token sumber 4, header 2, `retrieved=6`. covered 0, token gold 0. Tidak ada rank.
- Jawaban yang diharapkan:

| deret | P | token sumber | token header (A9) | retrieved_tokens | span_recall | token_precision | rr | fully_covered |
|---|---|---|---|---|---|---|---|---|
| off | (c1,c2,c3) | 11 | 0 | 11 | 5/5 | 2/11 | 1/2 | true |
| on | (c1) | 4 | 2 | 6 | 0/5 | 0/6 = 0 | 0 | false |

  Token sumber on (4) < off (11); `retrieved_tokens` on (6) ≤ B (11). `Setting` kembar berbeda hanya di `header_b` dan `setting_id`.
- Bug yang ditangkap: header tidak dihitung ke anggaran (on memberi `P=(c1,c2,c3)`, `retrieved` 11 + header 6 = 17 > B, atau hasil on = hasil off); header dihitung tetapi hanya untuk potongan pertama; header on dibuang dari penyebut presisi (0/4 = 0 tidak terdeteksi, tetapi `retrieved=4` salah); `precision` on `null` padahal `retrieved=6`; anggaran header-on diperlebar (`B + Σ header`); setting_id kembar sama.

### S2 — Sapuan anggaran: invarian token sumber on ≤ off, tepat sama di dua titik
- Masukan: T, ranking `C=(c1,c2,c3,c4)` sama untuk kedua deret, header baku T, gold dan packing seperti S1. Anggaran `B ∈ {5, 8, 11, 12, 13, 16, 20, 21}`.
- Langkah hitung (akumulasi off: 4, 9, 11, 14; akumulasi on: 6, 12, 17, 21):

| B | off P | sumber/header/ret | span | prec | rr | on P | sumber/header/ret | span | prec | rr |
|---|---|---|---|---|---|---|---|---|---|---|
| 5 | (c1) | 4/0/4 | 0 | 0 | 0 | () | 0/0/0 | 0 | null | 0 |
| 8 | (c1) | 4/0/4 | 0 | 0 | 0 | (c1) | 4/2/6 | 0 | 0 | 0 |
| 11 | (c1,c2,c3) | 11/0/11 | 1 | 2/11 | 1/2 | (c1) | 4/2/6 | 0 | 0 | 0 |
| 12 | (c1,c2,c3) | 11/0/11 | 1 | 2/11 | 1/2 | (c1,c2) | 9/3/12 | 1 | 1/6 | 1/2 |
| 13 | (c1,c2,c3) | 11/0/11 | 1 | 2/11 | 1/2 | (c1,c2) | 9/3/12 | 1 | 1/6 | 1/2 |
| 16 | semua | 14/0/14 | 1 | 1/7 | 1/2 | (c1,c2) | 9/3/12 | 1 | 1/6 | 1/2 |

  (span 1 = 5/5, 0 = 0/5; `rr` tanpa rank = 0. Presisi B=5 on: `retrieved=0` → `null`.)
- Jawaban yang diharapkan: tabel di atas. Invarian yang di-assert: untuk semua B, token sumber on ≤ off dan `retrieved_tokens` on ≤ B; sumber on < off pada B ∈ {5, 11, 12, 13, 16, 20}; sama (4 = 4 dan 14 = 14) pada B ∈ {8, 21} (A8). Recall on mencapai 1 baru di B=12, tepat saat akumulasi = B (off di B=11).
- Bug yang ditangkap: header ditambahkan sesudah pengemasan (retrieved on di B=11 = 11+6 = 17 > B, atau `P` on = `P` off di setiap B); `<` menggantikan `≤` pada akumulasi berheader (B=12: c2 ditolak padahal 12 ≤ 12, `P=(c1)`); invarian hanya ditegakkan pada satu B; biaya header dihitung untuk seluruh ranking dan bukan potongan yang masuk; `retrieved_tokens` melaporkan token sumber saja (B=21 on: 14, bukan 21).

### S3 — Biaya header dari teks dengan tokenizer run, bukan `tokens_local` atau `usage`
- Masukan: T. `C=(c1,c2)`, `B=12`, stop. `gold_spans=[[0,11)]` (`|G|=11`). HeaderB tersimpan:
  - c1: `header = "H1  H2"` (dua spasi di antara), `tokens_local = 99` (basi), `usage_input_tokens` run asal 1500.
  - c2: `header = "\nH3\n"` (newline di tepi), `tokens_local = 0` (basi).
- Langkah hitung: `tok("H1  H2") = 2`, `tok("\nH3\n") = 1` (A3). `cost(c1)=2+4=6`, `cost(c2)=1+5=6`; akumulasi 6, 12 ≤ 12. `P=(c1,c2)`. covered = `c1∩G` = 11; c2 tak beririsan. Token gold: token 0–3 → 4. `retrieved=12` (sumber 9 + header 3). Rank 1.
- Jawaban yang diharapkan: `P=(c1,c2)`, `retrieved_tokens=12`, `span_recall=11/11=1`, `gold_tokens_retrieved=4`, `token_precision=4/12=1/3`, `rr=1`, `fully_covered=true`.
- Bug yang ditangkap: memakai `tokens_local` (c1 cost 103 → `P=()`; atau 0 untuk c2 → total berbeda); memecah dengan satu spasi (`"H1  H2".split(" ")` = 3 → cost 7, akumulasi 13 > 12, `P=(c1)`); `strip` salah sehingga `"\nH3\n"` = 0 atau 2; memakai `usage` Spark sebagai biaya header; tokenizer header berbeda dari tokenizer sumber.

### S4 — Header hilang pada setting header-on: galat, bukan header kosong (A4)
- Masukan: T. Setting `header_b=true`, `C=(c1,c2)`, `B=12`. Store hanya memuat header untuk c1 (`"H1 H2"`); tidak ada untuk `chunk_id(c2)`.
- Langkah hitung: tidak ada angka; pengecekan jenis galat dan efek samping.
- Jawaban yang diharapkan: galat khusus (mis. `HeaderMissingError`) yang pesannya memuat `chunk_id` c2 dan `setting_id`; tidak ada `GridPoint` untuk setting itu; tidak ada entri cache grid sah untuk run itu; setting kembar `header_b=false` pada run yang sama tidak terdampak (hasilnya sama seperti tanpa kehadiran header store).
- Bug yang ditangkap: header hilang diperlakukan kosong (c2 cost 5 saja → `P=(c1,c2)` dengan `retrieved=11`, membuat on tampak lebih murah dari seharusnya); galat telan diam-diam; hasil sebagian di-cache; setting off ikut gagal.

### S5 — Kunci header: `chunk_id` termasuk `chunker_key`; header basi ditolak (A5)
- Masukan: T. Dua setting, span sama `[0,11)`:
  - Setting P: `chunker_key = kP`, `chunk_id = idP`.
  - Setting Q: `chunker_key = kQ`, `chunk_id = idQ` (≠ `idP`).
  - Store header: `idP → "H1 H2"` dari run B dengan `clean_sha256 = X`.
  - (a) run grid `clean_sha256 = X`, setting P header-on, `B=6`. (b) setting Q header-on pada run yang sama. (c) setting P header-on pada run grid `clean_sha256 = Y ≠ X`.
- Hitung: (a) cost 2+4 = 6 ≤ 6, `P=(c)`, `retrieved=6`. (b) tidak ada header untuk `idQ` → galat seperti S4. (c) run B asal `clean_sha256` X ≠ Y → header ditolak (jenis galat khusus, pesan memuat kedua hash).
- Jawaban yang diharapkan: (a) `retrieved_tokens=6`; (b) galat `idQ` hilang; (c) galat hash tidak cocok, tanpa `GridPoint`.
- Bug yang ditangkap: pencarian header berdasarkan `(doc_id, start, end)` saja (b memakai header P: lolos diam-diam); `chunker_key` tidak masuk kunci; header dari teks bersih lama dipakai setelah korpus berubah (c lolos, melanggar H-046).

### S6 — Gold dan offset tetap pada teks sumber, meski header berisi kata yang sama
- Masukan: T. Potongan `c=[6,17)` (token 2–5, teks `a2 a3 a4 a5`, tok 4). Header on: `"a4 a5 a2 a3"` (11 karakter, tok 4; kata persis sama dengan sumber; teks diindeks `header + "\n" + sumber`, panjang tambahan 12). `C=(c)`, `B=8`, stop. `gold_spans=[[9,14),[18,20)]` → `G={9..13}∪{18,19}`, `|G|=7`.
- Langkah hitung: cost 4+4 = 8 ≤ 8, `P=(c)`. `chars(c)=[6,17)`. `c∩G=[9,14)`=5 (posisi 18, 19 di luar c). Token gold: token 3 `[9,11)`, token 4 `[12,14)` → 2 (token 5 `[15,17)` bukan gold; token header tidak pernah gold). `retrieved=8`. Rank 1.
- Jawaban yang diharapkan: `gold_chars=7`, `covered_gold_chars=5`, `span_recall=5/7`, `gold_tokens_retrieved=2`, `retrieved_tokens=8`, `token_precision=2/8=1/4`, `rr=1`, `fully_covered=false`. Offset potongan tetap `[6,17)`; `gold_spans` tidak bergeser.
- Bug yang ditangkap: `chars(c)` diperpanjang panjang header+pemisah (`[6,29)` → menutup posisi 18–19, `span_recall=7/7`, `fully_covered=true`); offset dihitung pada string berheader; token header yang kata-katanya sama dengan token gold dicocokkan menurut teks (gold_tokens 4 atau 6, presisi 4/8 atau 6/8); `gold_chars` dihitung pada teks berheader.

### S7 — Dua deret frontier: partisi menurut header_b; frontier gabungan vs per deret (A1)
- Masukan: satu kelompok `(family=uupt, split=tune, budget=2000)`. Empat titik `GridPoint` (nilai ringkas; `dominated` belum dihitung):

| setting | header_b | mean_span_recall | mean_retrieved_tokens |
|---|---|---|---|
| A | false | 1/2 | 100 |
| B | false | 4/5 | 300 |
| C | true | 3/5 | 150 |
| D | true | 4/5 | 400 |

- Langkah hitung (dominasi EVAL-SPEC §9): A: tak ada yang recall ≥ 1/2 dengan token ≤ 100 selain dirinya → bebas. C (3/5, 150): B recall lebih tinggi tetapi 300 > 150; A recall lebih rendah → bebas. B: bebas. D (4/5, 400): B (4/5, 300) recall ≥ dan token < → D didominasi.
  - Frontier gabungan (dipilih, A1): `{A, B, C}`. Deret off: A, B; deret on: C, D, dengan D `dominated=true`.
  - Alternatif per deret: off `{A, B}`, on `{C, D}` (D bebas di dalam deret on karena recall 4/5 > 3/5).
- Jawaban yang diharapkan (A1 disetujui): `Frontier.point_ids = {A, B, C}` (urutan: token naik, lalu `setting_id`), `dominated(D)=true`; deret off = {A, B}, deret on = {C, D}, ditentukan dari `Setting.header_b`; titik dengan `header_b` berbeda tetapi anggaran dan split sama bersaing dalam kelompok yang sama. Bila operator memilih alternatif: frontier on = `{C, D}`.
- Bug yang ditangkap: frontier dihitung terpisah per deret tanpa disetujui (D lolos); deret ditentukan dari nama setting_id atau urutan; titik berheader dikeluarkan dari dominasi; titik header-on dan off yang beda anggaran digabung; deret on kosong menjatuhkan kelompok.

### S8 — Cakupan "hanya frontier" (H-017, A6): himpunan dari frontier tune header-off
- Masukan: kelompok `(uupt, tune, budget=2000)`, deret off sudah dihitung:

| setting | mean_span_recall (tune) | mean_retrieved_tokens (tune) |
|---|---|---|
| s1 | 1/2 | 100 |
| s2 | 7/10 | 200 |
| s3 | 3/5 | 250 |
| s4 | 9/10 | 400 |

  Config `header_b.scope = frontier_only`. Fake B (store header) tersedia untuk semua `chunk_id`. Varian (b): metrik held-out s3 diganti menjadi terbaik di semua setting (butir held-out tidak masuk pemilihan).
- Langkah hitung: s3 (3/5, 250) didominasi s2 (7/10 ≥ 3/5, 200 ≤ 250, kedua tegas). Frontier tune off = `{s1, s2, s4}`.
- Jawaban yang diharapkan: setting header-on yang dihitung = kembaran `{s1, s2, s4}` (3 titik); tidak ada kembaran s3. Varian (b): himpunan sama (nilai held-out tidak dibaca). Dengan `scope = all`: 4 kembaran. Nilai `scope` tercatat di konfigurasi sehingga `config_hash` berbeda antar kedua mode (S13). Deret on di data hanya berisi 3 titik; tidak ada galat "header hilang" untuk s3 karena kembarannya tidak diminta.
- Bug yang ditangkap: frontier diambil dari held-out (kebocoran, varian b mengubah himpunan); kembaran dibuat untuk semua setting walau `frontier_only`; s3 ikut karena frontier dihitung tanpa dominasi (hanya top-N recall); header diminta untuk setting yang tak ada di frontier sehingga memanggil galat; `scope` tidak tercatat.

### S9 — Granularitas B (H-038, A2): pasal vs ayat memengaruhi biaya
- Masukan: U + peta alamat. Tiga potongan beserta alamat awal: `X=[12,37)` (awal di Pasal 1 ayat (1); teks `(1) Aaa bbb.⏎(2) Ccc ddd.`, 6 token), `Y=[38,50)` (awal di Pasal 1 ayat (3); `(3) Eee fff.`, 3 token), `Z=[52,76)` (Pasal 2 tanpa ayat; `### Pasal 2⏎Ggg hhh iii.`, 6 token). `C=(X,Y,Z)`, stop. `gold_spans=[[38,50)]` (`|G|=12`).
  - Granularitas `pasal`: header unit Pasal 1 `"HP1a HP1b HP1c"` (3), Pasal 2 `"HP2a HP2b"` (2).
  - Granularitas `ayat`: ayat (1) `"HA1a HA1b"` (2), ayat (3) `"HA3a HA3b"` (2), Pasal 2 (tanpa ayat, satu unit) `"HP2a HP2b"` (2).
- Langkah hitung (A2: header unit pertama, dibayar per potongan):
  - `pasal`: biaya X 6+3 = 9, Y 3+3 = 6, Z 6+2 = 8.
  - `ayat`: biaya X 6+2 = 8, Y 3+2 = 5, Z 6+2 = 8.
  - B=14: pasal → akumulasi 9, 15 > 14 stop, `P=(X)`; ayat → 8, 13 (masuk), 21 > 14 stop, `P=(X,Y)`.
  - B=15: pasal → 9, 15 ≤ 15 → `P=(X,Y)` (header Pasal 1 dibayar dua kali: 3+3); Z 23 > 15. ayat → `P=(X,Y)` sama seperti B=14.
  - B=21: pasal → `P=(X,Y)` (23 > 21); ayat → 8, 13, 21 ≤ 21 → `P=(X,Y,Z)`.
  - Metrik gold `[38,50)` (Y; token `(3)`, `Eee`, `fff.` semuanya di G):
- Jawaban yang diharapkan:

| B | granularitas | P | sumber/header/ret | span_recall | token_precision | rr |
|---|---|---|---|---|---|---|
| 14 | pasal | (X) | 6/3/9 | 0/12 = 0 | 0/9 = 0 | 0 |
| 14 | ayat | (X,Y) | 9/4/13 | 12/12 = 1 | 3/13 | 1/2 |
| 15 | pasal | (X,Y) | 9/6/15 | 1 | 3/15 = 1/5 | 1/2 |
| 15 | ayat | (X,Y) | 9/4/13 | 1 | 3/13 | 1/2 |
| 21 | pasal | (X,Y) | 9/6/15 | 1 | 1/5 | 1/2 |
| 21 | ayat | (X,Y,Z) | 15/6/21 | 1 | 3/21 = 1/7 | 1/2 |

- Bug yang ditangkap: granularitas diabaikan (kedua hasil sama); header Pasal 1 di-dedup untuk Y pada `pasal` (Y cost 3 → B=14 memasukkan Y, hasil menyerupai ayat); header unit terakhir bukan pertama (X memakai header ayat (2) alih-alih `"HA1a HA1b"`; test memeriksa teks header yang dipakai, bukan hanya jumlah token); Pasal tanpa ayat tak punya header pada `ayat`; header B pada granularitas salah masuk kunci cache (S13).

### S10 — Kedua deret dijalankan dengan masukan identik kecuali header (A11)
- Masukan: runner grid dengan pipeline palsu yang mencatat argumen. Dua setting kembar `s` (`header_b=false`) dan `s+` (`header_b=true`): `family`, `chunker`, `chunk_size_tokens`, `overlap_tokens`, `retrieval_mode`, `budget_tokens=2000` sama. Butir sama `{i1,i2}`, split `tune`, tokenizer fake `toy-ws`/`1`, `packing=skip`.
- Hitung: tidak ada angka; periksa argumen yang diterima pengemas dan isi `RunRecord`.
- Jawaban yang diharapkan: `setting_id(s) ≠ setting_id(s+)`; pengemas menerima `B=2000` untuk keduanya (bukan `2000 + Σ header` atau `2000 − Σ header`), `packing=skip` untuk keduanya, tokenizer sama; himpunan butir dan `split` sama; hanya `hdr(c)` yang berbeda (kosong untuk `s`). `RunRecord.tokenizer = {name:"toy-ws", version:"1"}` dan `RunRecord.packing = "skip"` satu nilai untuk run; `ItemMetrics.setting_id` memakai setting masing-masing.
- Bug yang ditangkap: `s+` memakai packing default `stop` sementara `s` memakai `skip`; anggaran `s+` dikurangi/ditambah sebelum pengemasan (menghitung header dua kali atau di luar anggaran); `setting_id` kembar sama (hasil saling menimpa); `header_b` tidak masuk `setting_id`.

### S11 — Agregat deret: header menambah `mean_retrieved_tokens`
- Masukan: tiga butir, ringkasan `ItemMetrics` per deret (dari kalkulator):

| butir | gold? | off: span / retrieved | on: span / retrieved |
|---|---|---|---|
| i1 | ya | 1 / 4 | 1/2 / 6 |
| i2 | ya | 1/2 / 9 | 1/2 / 12 |
| i3 | tidak | null / 5 | null / 8 |

- Langkah hitung (A12: butir bergold saja): off: `mean_span_recall=(1+1/2)/2=3/4`, `mean_retrieved_tokens=(4+9)/2=13/2`; on: `(1/2+1/2)/2=1/2`, `(6+12)/2=9`. `fully_covered_count`: off `{covered:1,total:2}` (i1 penuh), on `{covered:0,total:2}`.
- Jawaban yang diharapkan: titik off `(3/4, 13/2)`, titik on `(1/2, 9)`; sumbu X titik on mencakup token header.
- Bug yang ditangkap: sumbu X on dihitung dari token sumber saja (4 dan 9 → 13/2, titik on tampak sama dengan off); butir tanpa gold masuk rata-rata (off 6, on 26/3; recall `/3`); rata-rata gabungan bukan per butir; `total` "x of y" menghitung i3.

### S12 — Indeks retrieval: header-off tanpa jejak header; header-on memuat header
- Masukan: T. Dua potongan: `c1=[0,11)` (teks `a0 a1 a2 a3`), `c2=[12,26)` (teks `a4 a5 a6 a7 a8`). Header: c1 `"H1"`, c2 `"ZZ H2"` (`ZZ` tidak ada di teks sumber manapun). Query `"ZZ"`. Retrieval BM25 sungguhan pada korpus dua potongan ini (tanpa stemming; skor tidak dikunci angkanya).
- Langkah hitung: indeks off berisi teks sumber persis; indeks on berisi header dan teks sumber (A7). Kata `ZZ` ada hanya di indeks on, hanya di c2.
- Jawaban yang diharapkan: teks terindeks off(c1) = `"a0 a1 a2 a3"` dan off(c2) = `"a4 a5 a6 a7 a8"` persis; teks terindeks on(c2) memuat `ZZ`, `H2`, dan seluruh `a4 … a8`; off: skor c1 = c2 = 0 untuk query `ZZ` dan `ZZ` tidak ada di kosakata indeks; on: c2 skor > 0, c1 skor 0, c2 peringkat 1. Offset `[start,end)` dan `chunk_id` kedua potongan sama di kedua deret. Indeks off dan on adalah dua indeks terpisah (mengubah satu tidak mengubah yang lain).
- Bug yang ditangkap: satu indeks dibagi dua deret (header bocor ke off, `ZZ` ada di kosakata off; atau header tidak ada di on); header menggeser offset potongan; indeks on tidak memuat header (query `ZZ` tidak menemukan c2, sehingga header B tidak berpengaruh dan frontier on identik dengan off).

### S13 — Kunci cache grid mencakup identitas header (A10)
- Masukan: pipeline palsu dengan penghitung panggilan. Enam run berurutan pada konfigurasi grid yang sama kecuali yang disebut:
  1. R1: awal (`scope=all`, granularitas `pasal`, `prompt_hash=p1`, store header `e1`).
  2. R2: identik dengan R1.
  3. R3: `prompt_hash=p2` (store header baru `e2` hasil prompt berbeda).
  4. R4: granularitas `ayat`.
  5. R5: `scope=frontier_only`.
  6. R6: identik dengan R1 lagi.
- Hitung: hitung pemanggilan pipeline hitung-metrik untuk deret on.
- Jawaban yang diharapkan: R1 menghitung (>0 panggilan); R2 tidak ada panggilan (baca cache); R3, R4, R5 masing-masing menghitung deret on baru (kunci berbeda; hasil R1 tidak dipakai); R6 tidak ada panggilan (hasil R1 masih ada). Tidak ada run yang mengembalikan deret on dari kunci lain. Apakah deret off ikut dihitung ulang di R3–R5 tidak dikunci (A10).
- Bug yang ditangkap: header tidak masuk kunci (R3, R4, R5 mengembalikan hasil R1 yang basi); kunci mengandung waktu atau `run_id` acak (R2 dan R6 menghitung ulang); cache tertimpa oleh R3 sehingga R6 salah (R6 mengembalikan hasil R3).
