## Konvensi umum skenario

- Semua id (butir, setting) buatan. Test nyata memakai pipeline palsu (fake) yang mengembalikan `ItemMetrics` dari tabel di skenario; tidak ada chunker, retrieval, atau tokenizer sungguhan (kalkulator metrik di luar scope M1.4).
- Tabel konfigurasi buatan: `config/grid` tiruan diinjeksi (belum ada berkas `config/grid.toml` di repo saat skenario ini disusun). Test tidak membaca config nyata.
- Penyederhanaan metrik: kecuali S23 (sengaja memakai `gold_chars` berbeda), semua butir punya `gold_chars = 10`; `covered` diberikan per butir; `span_recall = covered/10`. Di satu setting, `retrieved_tokens` dan `token_precision` bernilai konstan per butir (kecuali ditulis lain), sehingga `mean_retrieved_tokens` dan `mean_token_precision` sama dengan konstanta itu. Butir tanpa gold: `span_recall = null`, `token_precision = null`, dikeluarkan dari rata-rata recall dan precision.
- Aritmetika pembanding (recall, selisih, precision) di test memakai bilangan rasional/desimal eksak atau bilangan bulat, bukan float mentah, supaya derau float tidak menutupi bug (lihat S12 dan S16).
- RNG pengacak split tidak ditetapkan spec (lihat Asumsi A1). Karena itu skenario split menguji invarian (jumlah per stratum, keanggotaan, determinisme), dan hanya menyebut butir spesifik bila hasilnya terpaksa (forced). Test tidak boleh mengunci urutan acak tertentu.
- Skenario pemilihan dengan seri di tune (S16–S19) juga menyertakan metrik held-out yang akan membalik pilihan bila dibaca. Berlaku pula uji metamorfik: mengganti seluruh metrik held-out tidak boleh mengubah pilihan.
- "Pesan jelas" (gagal) diuji sebagai: jenis galat khusus split, dan pesan memuat jumlah kontrol yang ditemukan serta jumlah yang dibutuhkan (angka 3).

## Asumsi dan pilihan yang perlu disetujui operator

1. **Algoritma acak.** §8 butir 2 menyebut "diurutkan menurut `id`, diacak dengan `seed`" tanpa menyebut generator. Pilihan: test tidak mengunci hasil acak spesifik; hanya invarian + determinisme + independen urutan masukan. Alternatif: pin algoritma (mis. generator tertentu dengan urutan sort leksikografis `id`) dan tulis hasil golden. Konsekuensi alternatif: lebih tajam, tetapi mengikat implementasi dan versi pustaka.
2. **Pembulatan per stratum.** Usulan: jumlah held-out stratum berukuran `n` = `round(0.4 × n)` ke bilangan bulat terdekat. Untuk `0.4`, hasil `0.4n` tidak pernah tepat .5 (pecahan kelipatan 0.2), jadi round-half-up dan round-half-even sama. Hasil: n=1→0, 2→1, 3→1, 4→2, 5→2, 6→2, 7→3, 8→3, 9→4, 10→4. Alternatif: floor (n=4→1, kontrol makin sering kurang dari 3), ceil (n=6→3, held-out membengkak), pembulatan global dengan largest-remainder (total tepat 40%, tetapi bukan "per stratum" seperti tertulis di H-049). S3 memakai rasio 0.25 sehingga hasil `0.25n` tidak pernah tepat .5 untuk n genap yang dipakai; bila operator ingin kasus tepat .5 (mis. rasio 0.5, n=5) dikunci, putuskan half-up vs half-even.
3. **Cara "menambah kontrol lebih dulu".** Usulan: butir `operator` yang masih tune dipindahkan ke held-out (held-out membesar melebihi 40%; butir tune non-kontrol dan butir held-out spark tidak diubah; tidak ada butir held-out spark dikeluarkan untuk "menyeimbangkan"). Pemilihan butir yang dipindah: urutan deterministik (stratum operator berurutan leksikografis `(origin, mode)`, lalu posisi dalam urutan acak seed). Test hanya menegaskan jumlah dan keanggotaan, bukan butir yang mana (kecuali kasus terpaksa S5). Alternatif: tukar (swap) dengan butir spark held-out agar total tetap 40%; atau tarik hanya dari stratum yang paling banyak tune.
4. **Butir baru (split_version naik).** Usulan "target kumulatif": untuk tiap stratum, `target = round(ratio × N_total_stratum)`; butir baru yang masuk ke stratum itu mengisi `max(0, target − held_lama)` slot held-out (dibatasi jumlah butir baru), sisanya tune; assignment lama tidak berubah. Alternatif "per batch": `round(ratio × n_baru)` hanya atas butir baru (S8 memberi kasus yang membedakan keduanya: stratum `(spark_disetujui, literal)` 4 + 2 butir baru). Butir baru mana yang dapat slot saat hanya sebagian: ditentukan urutan `id` + seed (test tidak mengunci). Syarat ≥3 kontrol tidak dapat turun karena assignment lama tetap.
5. **Versi tanpa perubahan.** Usulan: memanggil split lagi dengan himpunan butir yang sama tidak menaikkan `split_version` dan mengembalikan record identik. Alternatif: selalu naik versi. Dan seed/rasio di `config/grid` yang berubah setelah record ada: usulan record lama menang (seed dan rasio tersimpan dipakai; assignment tidak berubah); alternatif: galat jelas karena config berbeda dari record. S9 menerima dua-duanya sebagai "lulus", asalkan assignment lama tidak pernah berubah; operator memilih satu.
6. **Konversi "selisih ≤ 1 butir" ke selisih recall rata-rata (tafsir).** Usulan: 1 butir = `1/n_tune_gold` dalam satuan rata-rata span recall, dengan `n_tune_gold` = jumlah butir tune yang punya gold (penyebut rata-rata recall; butir tanpa gold tidak dihitung). Pembanding inklusif (`≤`), dihitung eksak (rasional/integer: `selisih_jumlah_recall ≤ 1`). Himpunan kandidat = setting dengan `mean_span_recall ≥ terbaik − 1/n_tune_gold` (jarak diukur ke yang terbaik, bukan berantai antar-pasangan). Alternatif: (a) penyebut `n_tune` termasuk butir tanpa gold; (b) selisih hitungan `fully_covered` ≤ 1; (c) selisih berantai (transitif). Perbedaan (a) ditangkap S16.
7. **Urutan "paling sederhana" (config/grid).** H-034 hanya menyebut tiga sumbu: tanpa header B, overlap lebih kecil, satu mode retrieval. Usulan: kunci leksikografis dengan prioritas header B (off < on), lalu `overlap_tokens` (null dibaca 0, lebih kecil lebih sederhana), lalu urutan mode dari config (tiruan skenario sengaja bukan alfabetis dan bukan urutan enum: `hybrid < dense < bm25`; urutan nyata milik operator). Ukuran potongan tidak masuk kunci, sehingga dua setting yang hanya berbeda ukuran dianggap seri sederhana dan lanjut ke precision. **S18 bergantung pada pilihan ini**: bila operator memasukkan ukuran potongan ke kunci (mis. lebih kecil = lebih sederhana), S18 harus ditulis ulang. Alternatif: overlap lebih dulu daripada header (S17 menunjukkan pilihan berbeda); ukuran lebih kecil/besar dimasukkan kunci; skor jumlah. Operator menetapkan urutan prioritas dan mengisi `config/grid`.
8. **Pemilihan dari semua setting tune pada anggaran itu, bukan hanya dari titik frontier.** Titik sederhana dalam pita ≤ 1 butir bisa terdominasi (S16 sengaja begitu) dan tetap boleh terpilih. Alternatif: batasi pemilihan ke frontier tune.
9. **Frontier per kelompok (family, split, budget_tokens).** Sesuai bentuk `Frontier` di DATA-CONTRACTS §10; titik beda anggaran atau beda split tidak saling mendominasi. Alternatif: satu frontier gabungan lintas anggaran untuk grafik (U2). Bila dipilih, S13 diubah. Urutan `point_ids` di hasil: `mean_retrieved_tokens` naik, lalu `setting_id` naik (usulan; kosmetik).
10. **"Pemilihan per anggaran".** Dilakukan terpisah per `budget_tokens`; setting_id mengandung `budget_tokens` (field `Setting`), jadi kandidat tiap anggaran adalah himpunan setting_id yang berbeda.
11. **Rata-rata `mean_retrieved_tokens`** dihitung atas semua butir split itu yang punya `retrieved_tokens` (termasuk butir tanpa gold, karena konteks tetap diambil). Skenario memakai konstanta per setting sehingga tidak bergantung pilihan ini; bila operator ingin hanya butir bergold, ubah. Dicatat sebagai tidak dikunci skenario.
12. **Akta:** `family = akta` tidak menghasilkan `SplitRecord` dan tidak ada pemilihan (H-054). Pemanggilan fungsi split untuk akta adalah galat pemanggil atau no-op yang jelas; S10 menerima keduanya selama tidak ada `SplitRecord` dan tidak gagal karena syarat ≥3 kontrol. **Pertanyaan operator (konflik kontrak):** `DATA-CONTRACTS` §10 mendefinisikan `ItemMetrics.split`, `GridPoint.split`, dan `Frontier.split` sebagai enum `tune` / `held_out` saja, sedangkan EVAL-SPEC §9 memakai `transfer` hanya di tabel laporan. Pilihan: (a) perluas enum dengan `transfer`; (b) `split = null` untuk akta; (c) `transfer` hanya di lapisan laporan. S10 sengaja tidak mengunci nilainya, hanya melarang `tune`/`held_out`. Perlu dicatat sebagai isu "Menunggu operator" sebelum S10 disetujui.
13. **Hash cache grid** = `hash(clean_sha256, config_hash, item_set_hash, split_version)` (ARCHITECTURE §8). Skenario S22 mengasumsikan keempat komponen masuk kunci. "Tidak menghitung ulang" diuji lewat penghitung panggilan pada pipeline palsu, bukan waktu. S22 run 6 (27 panggilan) mengunci cache pada granularitas run (satu kunci per run grid); cache lebih halus per (setting, butir), yang memberi 3 panggilan di run 6, adalah alternatif dan membuat S22 harus ditulis ulang.
14. **Validasi sebelum acak (S6).** Skenario tidak mensyaratkan jumlah panggilan RNG tertentu: hanya bahwa tidak ada percobaan ulang dengan seed lain dan tidak ada record tersimpan. Alternatif: implementasi yang memvalidasi kontrol total sebelum mengacak (nol panggilan RNG) juga sah; mengunci "tepat satu kali" ditolak karena mengikat urutan implementasi.
15. **Ekspansi grid (S21)** mengasumsikan produk Cartesian penuh `header_b × retrieval_mode` untuk setiap varian chunker (H-012). Konfirmasi ke operator; bila sebagian kombinasi dikecualikan, jumlah 24 berubah.
16. **Agregasi:** `mean_span_recall` dan `mean_token_precision` = rata-rata per butir atas butir bergold (EVAL-SPEC §4), bukan pooled karakter/token (S23).

## Skenario

### S1 — Split dasar: jumlah per stratum, pembulatan terdekat
- Masukan: `family = uupt`, `held_out_ratio = 0.4`, `seed = 7`. 20 butir (id `u01`..`u20`): stratum `(operator, literal)` = `u01..u05` (5); `(operator, parafrase)` = `u06..u10` (5); `(spark_disetujui, literal)` = `u11..u14` (4); `(spark_disetujui, parafrase)` = `u15..u20` (6). Masukan diberikan dalam urutan campur.
- Langkah hitung: 0.4×5 = 2.0 → 2; 0.4×5 → 2; 0.4×4 = 1.6 → 2; 0.4×6 = 2.4 → 2. Held-out total 8, tune 12. Kontrol di held-out = 2 + 2 = 4 (≥ 3, tanpa pemindahan tambahan).
- Jawaban yang diharapkan: held-out per stratum persis 2, 2, 2, 2 (bukan 2, 2, 1, 2 atau 2, 2, 2, 3). `SplitRecord`: `split_version = 1`, `seed = 7`, `held_out_ratio = 0.4`, `strata = ["origin","mode"]`, `control_in_held_out = 4`, 20 assignment (tiap butir tepat satu), semua `added_in_version = 1`.
- Bug yang ditangkap: floor (stratum 4 → 1), ceil (stratum 6 → 3), pembulatan global (8 total tetapi distribusi bebas, mis. 3 di satu stratum), strata hanya satu sumbu, butir hilang atau ganda, `0.4` hardcode (lihat S3), `control_in_held_out` salah hitung.

### S2 — Stratum kecil: ukuran 1 dan 2, tanpa pemindahan kontrol
- Masukan: ratio 0.4, seed 11. Stratum: `(operator, literal)` 7 butir `a1..a7`; `(operator, parafrase)` 1 butir `b1`; `(spark_disetujui, literal)` 2 butir `c1,c2`; `(spark_disetujui, parafrase)` 3 butir `d1..d3`. Total 13.
- Langkah hitung: 0.4×7 = 2.8 → 3; 0.4×1 = 0.4 → 0; 0.4×2 = 0.8 → 1; 0.4×3 = 1.2 → 1. Held-out = 3+0+1+1 = 5; tune = 8. Kontrol held-out = 3 + 0 = 3 (tepat memenuhi syarat, tidak ada pemindahan).
- Jawaban yang diharapkan: held-out per stratum 3, 0, 1, 1. `b1` terpaksa tune (ukuran 1 → 0 held-out). `control_in_held_out = 3`. Tidak ada galat.
- Bug yang ditangkap: ceil memaksa `b1` ke held-out; floor menghasilkan `c` 0 dan `a` 2 sehingga kontrol 2 lalu memicu pemindahan tak perlu; round Python half-even bukan masalah di sini tetapi implementasi `int(x + 0.5)` salah ukuran; stratum 1 butir dibagi nol/galat; batas kontrol `> 3` alih-alih `>= 3` (kasus tepat 3 dianggap kurang lalu memindah kontrol ke-4: kontrol held-out akan 4 ≠ 3).

### S3 — Rasio dari config, bukan literal 0.4
- Masukan: config tiruan `held_out_ratio = 0.25`, seed 3. Stratum: `(operator, literal)` 8, `(operator, parafrase)` 8, `(spark_disetujui, literal)` 4, `(spark_disetujui, parafrase)` 4. Total 24.
- Langkah hitung: 0.25×8 = 2; 0.25×8 = 2; 0.25×4 = 1; 0.25×4 = 1. Held-out 6, tune 18. Kontrol held-out = 4.
- Jawaban yang diharapkan: held-out per stratum 2, 2, 1, 1; `SplitRecord.held_out_ratio = 0.25`. (Dengan literal 0.4 hasilnya 3, 3, 2, 2 = 10.)
- Bug yang ditangkap: nilai 0.4 ditanam di kode (AGENTS: nilai konfigurasi dilarang literal); rasio tidak dicatat di record.

### S4 — Pemindahan kontrol parsial (butir kontrol kurang dari 3 setelah pembulatan)
- Masukan: ratio 0.4, seed 5. Stratum: `(operator, literal)` 3 butir `o1..o3`; `(operator, parafrase)` 2 butir `p1,p2`; `(spark_disetujui, literal)` 6 butir `s1..s6`; `(spark_disetujui, parafrase)` 9 butir `t1..t9`. Total 20.
- Langkah hitung: dasar 0.4×3 = 1.2 → 1; 0.4×2 = 0.8 → 1; 0.4×6 = 2.4 → 2; 0.4×9 = 3.6 → 4. Held-out dasar 8; kontrol held-out dasar = 1+1 = 2 < 3. Tambah 1 kontrol dari tune (tersisa tune operator: 2 di `o`, 1 di `p`), held-out menjadi 9, kontrol = 3.
- Jawaban yang diharapkan: held-out total 9; `control_in_held_out = 3`; held-out spark tetap 2 (literal) dan 4 (parafrase); tepat satu butir operator ekstra dipindah (hasil `(o_held, p_held)` = `(2,1)` atau `(1,2)`); butir tune spark dan butir held-out spark tidak berubah dibanding pembagian dasar (diuji dengan membandingkan ke pembagian yang sama seed tanpa langkah pemindahan, yang tersedia sebagai fungsi tes/hitung dasar atau dihitung ulang lewat jumlah per stratum).
- Bug yang ditangkap: syarat tidak ditegakkan (kontrol 2); menukar dengan butir spark held-out (spark literal 1 atau parafrase 3); menarik semua kontrol tune ke held-out (kontrol 5); mengacak ulang seluruh split sampai syarat terpenuhi (melanggar "bukan diacak ulang diam-diam"; terdeteksi karena butir spark held-out berubah dari pembagian dasar); `control_in_held_out` tidak diperbarui.

### S5 — Pemindahan kontrol terpaksa: seluruh kontrol masuk held-out
- Masukan: ratio 0.4, seed 21. Stratum: `(operator, literal)` 2 butir `o1,o2`; `(operator, parafrase)` 1 butir `p1`; `(spark_disetujui, literal)` 5 butir `s1..s5`; `(spark_disetujui, parafrase)` 5 butir `t1..t5`. Kontrol total tepat 3.
- Langkah hitung: dasar 0.8→1, 0.4→0, 2.0→2, 2.0→2; kontrol held-out dasar = 1 (< 3). Butuh 2 lagi; sisa kontrol di tune tepat 2, jadi semua 3 pindah.
- Jawaban yang diharapkan (deterministik, tanpa bergantung RNG): `o1`, `o2`, `p1` semuanya held-out; held-out spark 2 dan 2; total held-out 7; `control_in_held_out = 3`; tune hanya butir spark: literal 3, parafrase 3 (total 6). Tidak ada galat.
- Bug yang ditangkap: galat prematur "kontrol kurang" karena memeriksa setelah pembulatan dan sebelum pemindahan; hanya memindah 1 kontrol; menolak batas "tepat 3 kontrol total".

### S6 — Kontrol total kurang dari 3: gagal jelas, tanpa efek samping
- Masukan A: 12 butir, hanya 2 butir `operator` (`o1` literal, `o2` parafrase) dan 10 butir `spark_disetujui` tersebar di dua mode. Masukan B: 12 butir tanpa satu pun `operator`. Ratio 0.4, seed 1.
- Langkah hitung: A: kontrol total 2 < 3, mustahil dipenuhi walau semua kontrol dipindah. B: 0 < 3.
- Jawaban yang diharapkan: pemanggilan gagal dengan galat khusus split; pesan memuat jumlah kontrol ditemukan (A: 2; B: 0) dan jumlah dibutuhkan (3). Tidak ada `SplitRecord` tersimpan (penyimpanan tiruan tetap kosong), tidak ada percobaan ulang dengan seed lain (tidak ada pengacakan kedua dengan seed lain; lihat Asumsi A14), hasil parsial tidak dikembalikan.
- Bug yang ditangkap: split sukses dengan kontrol 2 atau 0; mengacak ulang dengan seed berbeda sampai "lolos"; menyimpan record sebelum validasi; pesan generik tanpa angka; pembagian oleh nol bila tak ada kontrol.

### S7 — Determinisme seed dan independen urutan masukan
- Masukan: himpunan S1 (20 butir). Panggil split (penyimpanan kosong baru tiap panggilan): (a) seed 7 urutan asli; (b) seed 7 urutan dibalik; (c) seed 7 urutan acak lain; (d) untuk seed `k` dalam 1..20, ambil himpunan held-out stratum `(spark_disetujui, parafrase)` (6 butir, 2 held-out).
- Langkah hitung: (a)=(b)=(c) harus sama persis. Di (d), jumlah pilihan 2-dari-6 adalah 15; dengan 20 seed berbeda, sangat tidak mungkin semua sama bila seed dipakai.
- Jawaban yang diharapkan: assignment (a), (b), (c) identik byte per byte (dibandingkan sebagai dict `item_id → split`, urutan list assignment juga sama, yaitu terurut `id`). Pada (d), minimal dua himpunan held-out berbeda muncul (seed benar-benar dipakai). `SplitRecord.seed` sama dengan seed masukan. Jalankan (a) dua kali di proses terpisah (atau dengan `PYTHONHASHSEED` berbeda): hasil sama.
- Bug yang ditangkap: iterasi `set`/dict yang bergantung hash atau urutan masukan; lupa mengurutkan `id` sebelum acak; seed diabaikan (global RNG, waktu); seed tercatat salah; urutan list assignment bergantung masukan (menggagalkan hash `item_set_hash`/hasil grid).

### S8 — Butir baru: split_version naik, assignment lama tidak berubah, aturan stratum sama
- Masukan: split v1 hasil S1 (seed 7), tersimpan. Lalu config tetap. Tambahkan 4 butir disetujui belakangan: `z1` `(spark_disetujui, parafrase)`; `z2`, `z3` `(spark_disetujui, literal)`; `z4` `(operator, literal)`. Panggil split dengan 24 butir.
- Langkah hitung (usulan target kumulatif, Asumsi A4): 
  - `(spark, parafrase)`: N lama 6 + 1 = 7; target = round(0.4×7 = 2.8) = 3; held lama 2; butuh 1 dari 1 butir baru → `z1` **held-out** (terpaksa).
  - `(spark, literal)`: N = 4 + 2 = 6; target = round(2.4) = 2; held lama 2; butuh 0 → `z2`, `z3` **tune** (terpaksa). (Alternatif per-batch: round(0.4×2 = 0.8) = 1 → satu held-out; berbeda.)
  - `(operator, literal)`: N = 5 + 1 = 6; target = 2; held lama 2; butuh 0 → `z4` **tune**.
  - Held-out total = 8 + 1 = 9; kontrol held-out tetap 4.
- Jawaban yang diharapkan: `split_version = 2`; 20 assignment lama identik dengan v1 (split dan `added_in_version = 1`); `z1 → held_out`, `z2, z3, z4 → tune`, semuanya `added_in_version = 2`; `control_in_held_out = 4`; `seed` dan `held_out_ratio` tetap yang tercatat di v1.
- Bug yang ditangkap: mengacak ulang seluruh himpunan (assignment lama berubah); versi tidak naik atau `added_in_version` salah; pembulatan per-batch (z2/z3 salah satu held-out, z1 tune); butir baru semua tune atau semua held-out; menimpa record lama sehingga v1 hilang (bila penyimpanan memegang riwayat, v1 tetap terbaca).

### S9 — Tanpa butir baru: idempoten; config berubah tidak mengubah assignment
- Masukan: record v2 dari S8 dalam penyimpanan. (a) Panggil split dengan 24 butir yang sama dan config sama. (b) Panggil dengan config tiruan `seed = 999` dan `held_out_ratio = 0.5`, himpunan butir sama.
- Langkah hitung: (a) tidak ada butir baru, tidak ada yang berubah (Asumsi A5). (b) record tersimpan menang atau galat jelas; assignment tidak boleh berubah.
- Jawaban yang diharapkan: (a) record identik dengan v2, `split_version = 2` (tidak naik ke 3); (b) salah satu: record v2 dikembalikan tak berubah (seed 7, ratio 0.4), ATAU galat jelas "config berbeda dari record" tanpa mengubah penyimpanan; dalam kedua kasus `assignments` sama dengan v2 (operator memilih satu, Asumsi A5).
- Bug yang ditangkap: versi naik tanpa alasan; split diacak ulang saat seed config berubah; `SplitRecord` ditimpa dengan seed/rasio baru tanpa menjalankan ulang (record bohong).

### S10 — Keluarga akta: tanpa split, tanpa pemilihan
- Masukan: `family = akta`, 5 butir sintetis `k1..k5` dengan `origin`: 2 `operator`, 3 `spark_disetujui` (sengaja kontrol < 3), `mode` campur. Pipeline palsu memberi metrik untuk satu setting.
- Langkah hitung: H-054: tidak ada `SplitRecord`; syarat ≥3 kontrol tidak berlaku (dua kontrol < 3 tidak boleh memicu galat).
- Jawaban yang diharapkan: tidak ada `SplitRecord` di penyimpanan; semua 5 butir ikut hitungan frontier akta sebagai satu kelompok; fungsi pemilihan profil untuk akta tidak mengembalikan pilihan (galat jelas atau "tidak ada pemilihan"); tidak ada keluaran akta (`ItemMetrics`, `GridPoint`, `Frontier`, laporan) yang bernilai `tune` atau `held_out`. Nilai label kelompok akta (`transfer`, `null`, lainnya) tidak dikunci: pertanyaan operator di Asumsi A12.

### S11 — Dominasi: ≥ dan ≤ dengan minimal satu tegas; titik identik

  - P5 `(a-5; 1200; 0.85)` 
  - P6 `(a-6; 2000; 0.90)` 
  - P7 `(a-7; 500; 0.30)` 
  - P8 `(a-8; 1000; 0.80)` (koordinat identik dengan P1).

  - P2: P1 punya y sama (0.80 ≥ 0.80) dan x lebih kecil (1000 < 1500): didominasi. 
  - P5: P4 punya x sama (1200 ≤ 1200) dan y lebih besar (0.90 > 0.85): didominasi.

### S12 — Kesamaan eksak yang rusak oleh float: rata-rata beda rute hitung
- Masukan: kelompok (uupt, tune, budget 2000). Dua setting, tiap setting 3 butir bergold (`gold_chars = 10`), `retrieved_tokens = 500` untuk semua butir. `f-1`: covered 0, 0, 3. `f-2`: covered 1, 1, 1.
- Langkah hitung: rata-rata eksak `f-1` = (0+0+3)/(10·3) = 1/10; `f-2` = (1+1+1)/30 = 1/10. Tokens 500 = 500: titik identik. (Dalam float double, `sum(c/10 for c in covered)/3` memberi `0.09999999999999999` untuk `f-1` dan `0.10000000000000002` untuk `f-2`; dihitung ulang dengan skrip.)
- Jawaban yang diharapkan: kedua titik masuk frontier, `dominated = false` untuk keduanya.
- Bug yang ditangkap: perbandingan float mentah atas rata-rata hitung-di-tempat: `f-1` tampak lebih kecil sehingga didominasi `f-2` (tokens sama, recall lebih besar tegas). Pembanding wajib eksak (rasional/integer) atau bertoleransi.

### S15 — Kebocoran held-out: memakai held-out mengubah pilihan
- Masukan: kelompok (uupt, budget 2000), dua setting dengan metrik per butir (`gold_chars = 10`). Tune = 10 butir bergold `i01..i10`. Held-out = 6 butir bergold `h1..h6`. Konstanta tokens/precision setara (agar tidak memengaruhi): tokens 1000, precision 0.20 untuk kedua setting.
  - Setting `T` (hybrid, header on, overlap 50, id `leak-T`): tune covered `[10,10,10,10,10,10,10,10,10,0]` (jumlah 90); held-out covered `[10,10,10,0,0,0]` (jumlah 30).
  - Setting `L` (bm25, header off, overlap 0, id `leak-L`): tune covered `[10,10,10,10,10,10,10,0,0,0]` (jumlah 70); held-out covered `[10,10,10,10,10,7]` (jumlah 57).
- Langkah hitung: mean tune `T` = 90/100 = 0.90; `L` = 70/100 = 0.70; selisih 0.20 = 2 butir (> 1/10 = 0.10): di luar pita, `T` menang. Mean held-out `T` = 30/60 = 0.50; `L` = 57/60 = 0.95. Penggabungan semua butir: `T` = 120/160 = 0.75; `L` = 127/160 = 0.79375.
- Jawaban yang diharapkan: profil terpilih = `leak-T`. Angka yang dilaporkan untuk profil terpilih = held-out: mean span recall 0.50 (30 dari 60 karakter gold held-out; laporan menampilkan hitungan mentah, bukan persen). Uji metamorfik: ganti seluruh metrik held-out menjadi `T`=1.0 dan `L`=0.0 (atau sebaliknya) → pilihan tetap `leak-T`; ganti metrik tune → pilihan berubah sesuai.
- Bug yang ditangkap: pemilihan memakai held-out saja (`L`); pemilihan memakai gabungan tune+held-out (`L`, 0.79375 > 0.75); laporan memakai angka tune (0.90) alih-alih held-out; filter `split` tidak diterapkan; held-out dibaca saat memecah seri.

### S16 — Pita "selisih ≤ 1 butir" dan pemecah sederhana; konversi ke selisih rata-rata
- Masukan: kelompok (uupt, budget 2000). Tune punya 11 butir: `i01..i10` bergold (`gold_chars = 10`), `i11` tanpa gold (recall null, precision null). `n_tune_gold = 10`. Kunci sederhana tiruan: header off < on; lalu overlap kecil; lalu mode `hybrid < dense < bm25`. Setting (tokens, precision konstan):
  - `s-x`: hybrid, header on, overlap 50; covered `[10]×8 + [0]×2` → recall 0.8; tokens 1500; precision 0.20.
  - `s-y`: dense, header off, overlap 50; recall 0.7 (`[10]×7+[0]×3`); tokens 1700; precision 0.30.
  - `s-z`: dense, header off, overlap 0; recall 0.7; tokens 1800; precision 0.25.
  - `s-w`: bm25, header off, overlap 0; recall 0.6 (`[10]×6+[0]×4`); tokens 900; precision 0.40.
  `i11` mendapat `retrieved_tokens` sama dengan konstanta dan tidak punya recall.
  Held-out (6 butir bergold; jumlah butir tertutup penuh dari 6): `s-x` 6, `s-w` 5, `s-y` 4, `s-z` 0 (pemenang held-out `s-x`).
- Langkah hitung: terbaik tune = `s-x` 0.8; 1 butir = 1/10 (Asumsi A6). Pita inklusif: recall ≥ 0.8 − 0.1 = 0.7 → {x, y, z}; `s-w` 0.6 (selisih 2 butir) keluar. Dalam pita: header off → {y, z}; overlap terkecil (0 < 50) → `z`. `z` (1800; 0.7) didominasi `x` (1500; 0.8) tetapi tetap boleh terpilih (Asumsi A8). Eksak: 8/10 − 7/10 = 1/10 ≤ 1/10. Penyebut 11: 1/11 ≈ 0.0909 < 0.1 → pita hanya {x}.
- Jawaban yang diharapkan: terpilih `s-z`; sama bila metrik held-out diganti (mis. `s-z` 6, `s-x` 0).
- Bug yang ditangkap: recall tertinggi saja (`s-x`); pita eksklusif `<` (`s-x`); selisih float (`0.8−0.7 = 0.10000000000000009 > 0.1`, `s-x`); penyebut 11 (`s-x`); precision sebelum sederhana (`s-y`); mengabaikan overlap (`s-y`); pita terlalu lebar (`s-w`); pemilihan dibatasi titik frontier (frontier hanya `s-w` dan `s-x`); held-out dipakai memecah seri atau digabung (`s-x`).

### S17 — Prioritas sumbu "sederhana": header, overlap, mode; overlap null
- Masukan A: kelompok (uupt, tune, budget 2000), 10 butir tune bergold; semua setting recall 0.5 (`[10]×5+[0]×5`), tokens 1000. Urutan mode tiruan `hybrid < dense < bm25` (bukan alfabetis, bukan enum `dense, bm25, hybrid`). Setting:
  - `p-1`: dense, header on, overlap 0, precision 0.50
  - `p-2`: bm25, header off, overlap 100, precision 0.40
  - `p-3`: hybrid, header off, overlap 100, precision 0.20.
  Held-out (butir tertutup penuh dari 6): `p-2` 6, `p-1` 3, `p-3` 0.
- Langkah hitung A: pita memuat ketiganya (recall sama). Prioritas header → {p-2, p-3}; overlap sama (100) → mode: hybrid < bm25 → `p-3`. Pembanding mode alfabetis atau enum (bm25 < hybrid) → `p-2`; tanpa kunci mode → precision → `p-2`.
- Masukan B: kelompok terpisah, recall 0.5, tokens 1000, header off, mode bm25 semua. `q-1`: `structure_handwritten`, overlap `null`, precision 0.10. `q-2`: `fixed_size`, overlap 32, precision 0.50. Held-out: `q-2` 6, `q-1` 0.
- Langkah hitung B: `null` dibaca 0 (Asumsi A7) → 0 < 32 → `q-1`, walau precision lebih rendah; implementasi tanpa kunci overlap jatuh ke precision → `q-2`. Bila `null` dibaca tak terhingga → `q-2`; bila memicu galat → gagal.
- Jawaban yang diharapkan: A → `p-3`; B → `q-1`. (Bila operator memutuskan overlap lebih dulu daripada header, A → `p-1`; skenario mengikuti A7.)
- Bug yang ditangkap: mode tidak ikut kunci atau dibandingkan alfabetis/enum (`p-2`); prioritas terbalik (`p-1`); header on dianggap lebih sederhana; overlap null tak terhingga atau galat (B); overlap tidak ikut kunci (B → `q-2`); held-out dipakai (`p-2`).

### S18 — Pemecah seri berantai: precision lalu token
- Masukan: kelompok (uupt, budget 2000); recall sama pada kedua setting tiap sub-kasus; kunci sederhana sama (header off, overlap 0, mode bm25); setting hanya berbeda ukuran potongan (ukuran tidak masuk kunci, Asumsi A7).
  - (a) 10 butir tune bergold, recall 0.6. `u-1`: precision konstan 3/10 (gold 300 dari retrieved 1000 tiap butir), tokens 1000; `u-2`: precision 1/4 (200/800), tokens 800. Held-out: `u-2` 6 dari 6, `u-1` 0.
  - (b) 3 butir tune bergold `j1..j3` (covered 10, 10, 0; recall 2/3 untuk kedua setting). `v-1`: retrieved 1000 per butir, gold tokens 200, 200, 200 → precision per butir 2/10, 2/10, 2/10; `v-2`: retrieved 900 per butir, gold tokens 90, 180, 270 → precision 1/10, 2/10, 3/10. Held-out: `v-1` 6 dari 6, `v-2` 0.
- Langkah hitung: (a) sederhana seri → precision 3/10 > 1/4 → `u-1` (walau tokens lebih banyak). (b) `v-1` = (2/10+2/10+2/10)/3 = 1/5; `v-2` = (1/10+2/10+3/10)/3 = 1/5 → seri eksak → tokens 900 < 1000 → `v-2`. Dalam float `sum(a/b)/3`: `v-1` = 0.20000000000000004, `v-2` = 0.19999999999999998; pembanding float memilih `v-1`. Catatan: gigitan float ini sempit (hanya rute `sum/n` naif; `statistics.mean` atau `math.fsum` memberi 0.2 untuk keduanya). Uji yang benar adalah aritmetika eksak (Fraction/integer); test tidak boleh bergantung pada kebetulan float.
- Jawaban yang diharapkan: (a) `u-1`; (b) `v-2`.
- Bug yang ditangkap: token sebelum precision (a → `u-2`); precision terendah atau token terbanyak dipilih; id terlalu cepat (b → `v-1`); precision float sehingga seri palsu (b → `v-1`); held-out dipakai (a → `u-2`, b → `v-1`).
